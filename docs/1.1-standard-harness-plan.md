# 1Agent 1.1 — Standard Harness (1ASH) development plan

Status: **proposed; design only, not implemented**
Date: 2026-11-18
Owner: product + runtime + evaluation
Working name: **1ASH — 1Agent Standard Harness**
Scope: an externally runnable, evidence-grade harness profile for 1Agent. Not a
public leaderboard and not a multi-vendor benchmark platform.

## 0. Decision in one page

We will build a **thin standard layer around the existing 1Agent harness**, not
a new agent framework and not a benchmark platform:

1. **Task contract** — a versioned, machine-readable task package (environment,
   instruction, permissions, budget, success checks, oracle, provenance).
2. **Runner** — adapters to Inspect AI, Harbor/Terminal-Bench and native
   `1agent run`; Docker/Kubernetes sandbox; bounded budgets; reproducible
   manifests.
3. **Trace IR** — one canonical event stream built from the 1Agent journal,
   Inspect logs and OpenTelemetry GenAI spans; call/result pairing, lineage,
   policy events and artifact hashes.
4. **Evidence scoring** — deterministic verifiers first, artifact verifier,
   optional calibrated judge, separate agent and harness score sheets.
5. **Signed report** — JSON + Markdown/HTML, reproducible command, environment
   digests, cost/latency, pass@k/pass^k, confidence intervals, failure
   attribution, limitations and ABC checklist answers.

The first release is **1ASH v0** with 30 tasks (20 public, 10 private holdout),
run through Inspect AI. We do **not** build a leaderboard, a marketplace, or a
reimplementation of SWE-bench/WebArena/OSWorld.

## 1. Research conclusions

### 1.1 What frontier practice says

| Source | Finding | Consequence for 1ASH |
|---|---|---|
| **Harness-Bench** (2026) | Agent performance depends on the model **and** the harness (context, tools, state, constraints, permissions, tracing, recovery). 106 tasks / 5,194 trajectories show large model–harness interaction. | Report at **model × harness configuration** level, never "model alone". |
| **TraceTrial-Bench** (2026) | 31.1% of task-success runs still fail at least one harness criterion; seven dimensions: context, execution, governance, lifecycle, observability, tools, verification. | Add a **harness score sheet** independent of task success. |
| **Terminal-Bench 2.0 / Harbor** (2026) | 89 container tasks; final-state tests; oracle solution; wall-clock timeouts; adversarial cheat audit; Harbor runs any CLI agent in-container. | Use containerized, final-state verification; adopt Harbor as an optional backend. |
| **METR Task Standard → Inspect** (2024–2026) | Task = environment + instructions + optional scorer; METR no longer maintains the standard and now uses Inspect. | Do **not** invent a task standard; implement an Inspect-compatible profile. |
| **Inspect AI** (UK AISI) | Dataset + solver + scorer; 200+ evals; Docker/K8s sandbox; external agents such as Claude Code/Codex/Gemini CLI. | Runner and sandbox substrate for v0; 1Agent is exposed as an external solver/agent. |
| **Agentic Benchmark Checklist (ABC)** (NeurIPS 2025) | Outcome validity, challenge validity, reporting; oracle, no-op baseline, contamination controls, confidence intervals, human baselines. | Every task must pass an ABC gate before entering the suite. |
| **AI Agents That Matter** (TMLR 2025) | Accuracy without cost is misleading; need Pareto curves, held-out sets, downstream-developer view, reproducibility. | Report cost/latency alongside every score; private holdout; no unbounded retries. |
| **OpenAI third-party evaluations playbook** (2026) | Results are harness/budget-dependent; separate capability elicitation, safeguard robustness and model comparison; report lower-bound framing. | Every report states harness and budget; no "capability ceiling" claim. |
| **OpenAI harness engineering** (2026) | Repo-as-truth, mechanical constraints, agent-readable docs and observability; humans steer, agents execute. | Treat the task package and report as code: schema-validated, reviewed, versioned. |
| **Anthropic long-running harnesses** (2025–2026) | Long tasks need handoff artifacts, progress state, one feature per session, separate evaluator, end-to-end testing. | Add multi-session/long-horizon tasks and measure handoff/recovery, not only one-shot success. |
| **AgentDojo** (2024–2026) | Prompt injection is a measurable agent property: benign utility, utility under attack, targeted ASR. | Safety suite reports ASR **and** utility under attack; not a single "safe/unsafe" label. |
| **A2A / MCP / OTel GenAI** | A2A = agent↔agent, MCP = agent↔tool, OTel GenAI = trace interop; all still evolving. | Interop layer only; 1Agent journal remains the source of truth. |

### 1.2 Six design conclusions

1. **Do not build a new benchmark framework.** Inspect already provides tasks,
   solvers, scorers, sandboxes and 200+ evals. Build a 1Agent profile and
   adapter on top.
2. **Harness is part of the measured system.** A 1Agent score is only meaningful
   as "1Agent harness vX + model Y + budget Z".
3. **Outcome alone is insufficient.** Score task success, harness reliability,
   cost, latency and safety separately.
4. **Evidence beats ranking.** The product need is procurement/audit trust, not
   a public leaderboard. A signed, reproducible report is the deliverable.
5. **Deterministic before semantic.** Use executable tests and state checks
   first; LLM judges only for criteria without an oracle, with calibration
   evidence and human sampling.
6. **Small, versioned, private holdout.** Start with 30 tasks and 10 private
   tasks; grow only after validity review. Saturation and contamination are
   maintenance problems, not one-time checks.

## 2. What 1ASH is and is not

### Is

- A **task package format** and **run/report contract** for evaluating 1Agent
  (and optionally other agents) in a reproducible environment.
- A **runner adapter** for Inspect AI, Harbor/Terminal-Bench and native
  `1agent run`.
- An **evidence layer** that normalizes traces, verifies artifacts and binds
  claims to hashes.
- A **quality gate** for 1Agent's own releases (rc/GA evidence).

### Is not

- A public leaderboard or ranking service.
- A multi-vendor judge platform.
- A replacement for SWE-bench, WebArena, OSWorld, GAIA, τ-bench or Terminal-Bench.
- An OS-level sandbox implementation; use Inspect/Docker/Kubernetes/Harbor.
- A claim of external audit, human calibration or GA by itself.

## 3. Design principles

1. **Task package is code.** YAML/JSON with schema version, reviewed like code.
2. **Environment is immutable.** Container image digest, tool versions, network
   policy, mounts and resource limits are recorded and enforced.
3. **Agent configuration is explicit.** Harness version, model snapshot,
   provider, temperature, seed, tool set, permissions, budget and retry policy.
4. **Final state over command transcript.** Success is checked from final
   artifacts/state where possible; traces explain *how*, not *whether*.
5. **Gates before partial credit.** Safety/security violations zero the task
   score; ordinary module failures lose only their weight.
6. **Cost is a first-class metric.** No unbounded retries; report wall time,
   tokens, API cost and tool calls.
7. **Reliability is pass^k, not best-of-k.** Report pass@k and pass^k; a lucky
   run is not a reliable harness.
8. **Every claim is reproducible.** Report includes the exact command, digests,
   seeds and versions; `1ash verify` re-checks the report and hashes.
9. **Human review is sampled and calibrated.** At least 100 sampled items,
   two raters, Cohen's κ reported; adjudication for disagreements.
10. **No silent scoring changes.** Task and scorer versions are immutable;
    changes create a new version and a migration note.

### 3.1 Key trade-offs

| Choice | We choose | Why | Cost |
|---|---|---|---|
| Build vs reuse | Reuse Inspect/Harbor; build only the 1Agent profile | Avoids a framework; 200+ evals and sandbox already exist | Upstream API drift, adapter work |
| Open vs proprietary | Open task/report schemas; keep private holdout | External verification needs an open contract | Competitors can reuse the schema |
| Outcome vs process | Report both; deterministic outcome first | Task success alone hides harness failures | More trace plumbing |
| Public vs private | Public tasks teach; private tasks protect validity | Prevents memorization and overfitting | Two task sets to maintain |
| Product vs platform | Evidence layer, not leaderboard | Trust is the current bottleneck; ranking is a different business | Less marketing surface |

The central bet: **a reproducible evidence report is more valuable to 1Agent
buyers than a public ranking**, and it is far cheaper to build without a
neutrality conflict.

### 4.3 Trace IR (`1ash.trace/v1`)

Canonical events:

- `run_started`, `run_stopped`
- `model_request`, `model_response` (content hash, token usage)
- `tool_call`, `tool_result` (call/result pairing, error code)
- `artifact_written`, `artifact_verified`
- `approval_requested`, `approval_decided`, `policy_denied`
- `context_compacted`, `session_handoff`, `subagent_spawned`, `subagent_finished`
- `budget_updated`, `verification_failed`, `recovery_attempt`

Each event has `run_id`, `seq`, `timestamp`, `type`, `span_id`, `parent_span_id`,
`harness_version`, and a hash of the previous event. Secrets and sensitive
content are redacted by default; content capture is opt-in.

External mapping:

- OTel GenAI: `invoke_agent`, `execute_tool`, `chat` spans;
  `gen_ai.agent.name`, `gen_ai.tool.name`, `gen_ai.conversation.id`.
- 1Agent journal: source of truth for native runs.
- Inspect logs: source for Inspect-driven runs.

## 5. Scoring model

### 5.1 Outcome score

Per task, use weighted modules:

```text
Q_i = gate_i * Σ w_ij * x_ij
```

- `x_ij ∈ {0,1}`: module passes/fails.
- `gate_i = 0` on safety/protected-resource/secret-exfiltration violation.
- Modules cover final state, tests, artifacts and required reporting.
- No-op baseline must fail; oracle baseline must pass.

### 5.2 Agent vs harness layers

Two score sheets per task:

- **Agent layer**: did the agent deliver the required outcome?
- **Harness layer**: did the harness preserve context, execute faithfully,
  enforce governance, manage lifecycle, emit observability, expose tools and
  verify results?

Harness dimensions (from TraceTrial-Bench, adapted):

| Dimension | Example checks |
|---|---|
| Context | cross-session recall, compaction loss, untrusted-content isolation |
| Execution | tool-call/result pairing, state fidelity, error recovery, resume |
| Governance | approval required/allowed, secret redaction, policy denial |
| Lifecycle | spawn/terminate, cleanup, handoff, cancellation |
| Observability | trace completeness, replayability, hash chain |
| Tools | discovery, schema errors, MCP call, timeout semantics |
| Verification | artifact hash/schema/preview, acceptance receipt, claim binding |

A task can be **agent-success but harness-fail**; both are reported.

### 5.3 Reliability and cost

- `pass@1`, `pass@k` (at least one of k), `pass^k` (all k).
- Wilson/bootstrap 95% confidence intervals.
- Mean/median cost, p95 latency, tool calls, tokens, retries.
- Accuracy–cost Pareto frontier; a higher score at unbounded retry is not a win.
- No-op, oracle and human baselines.

### 5.4 Judges and humans

- Deterministic checks first.
- LLM judge only for criteria without a deterministic oracle.
- Judge must have documented accuracy, self-consistency and human agreement;
  prompt hash and model snapshot recorded.
- Human sample: at least 100 items per release, two raters, κ reported;
  disagreements adjudicated.
- Judge scores never override a deterministic failure or a safety gate.

## 6. Safety and anti-gaming

- Default network `none`; allowlist only when the task requires it.
- Secrets injected by reference; never in task packages, logs or reports.
- Tool output treated as untrusted data; prompt-injection suite based on
  AgentDojo-style tasks (benign utility, utility under attack, ASR).
- Protected paths and forbidden actions zero the task score.
- Private holdout; canary strings; hidden tests; mutation testing.
- Oracle and no-op baselines in CI; adversarial "cheating agent" audit.
- Contamination scan: n-gram/embedding overlap with public corpora and prior
  runs; task retirement policy for saturation.
- Trace and report hash chain + signature; redaction checked before export.

## 9. Acceptance criteria for 1ASH v0

1. A third party can run `1ash run --task-set ... --run-spec ...` and
   `1ash verify report.json` in a clean container.
2. Oracle passes 100%; no-op fails at least 95%; a known-bad harness/agent
   fails at least one gate.
3. Report contains environment digest, subject config, model snapshot, seeds,
   budgets, cost/latency, pass@k/pass^k, CIs, failure classes and limitations.
4. Every task has an ABC checklist entry and two reviewers.
5. 30 tasks, 10 private; contamination scan and canary tasks pass.
6. Safety suite reports ASR and utility under attack; no secrets in traces.
7. Two independent runs of the deterministic suite produce identical scores.
8. 1Agent's own report is published with harness limitations; no claim of
   external audit or GA.

## 10. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Self-evaluation bias | private holdout, external reviewers, oracle/no-op, ABC |
| Harness/task coupling | configuration-level reporting, cross-harness adapters |
| Benchmark gaming | hidden tests, canary, mutation tests, adversarial audit |
| Judge bias | deterministic first, calibration, human sample, prompt hash |
| Sandbox escape | Inspect/Docker/K8s, no network, secret redaction, review |
| Maintenance burden | reuse Inspect/Harbor, start at 30 tasks, versioned sets |
| Conflict of interest | no public ranking; evidence report; independent sign-off |
| Cost blow-up | budget caps, Pareto reporting, bounded retries |
| Spec drift (OTel/A2A) | interop layer only; journal remains source of truth |

## 11. Parallel workstream — Operational Decision Ontology (1AO-P)

Status: **design proposal; 1.2 candidate, P0 can run inside 1.1**
Related: `docs/super-agent-ontology.md` (1AO), ADR-0149, ADR-0150

1ASH measures execution; 1AO models what the execution is *about*. Palantir's
2026 Ontology material makes the gap concrete: the valuable layer is not a
read-only graph, but a decision-centric model combining **Data + Logic +
Action + Security**, with decision data and decision lineage.

### 11.1 What we add

| Concept | Purpose | Current 1Agent anchor |
|---|---|---|
| `Decision` | The question being decided, context, chosen option, outcome | `TaskRequest`, `AgentAnswer`, `Goal` |
| `Option` / `Criterion` | Alternatives considered and the criteria used | clarify choices, plan proposals, answer assumptions |
| `ActionType` | Typed verb: parameters, preconditions, risk, reversibility, approval, side effects, postconditions, idempotency | `ActionCard`, `CuaAction`, tool specs |
| `ActionInvocation` | One executed action with policy/approval/outcome | `ToolCalled`/`ToolObserved`, action log |
| `PolicyDecision` / `Approval` | Why the action was allowed/denied and who approved | `ExecutionGate`, `AuthorityProfile`, approval cards |
| `Outcome` | What actually happened, verified artifact/state | `verify_artifact`, `acceptance_gate`, completion gate |
| `Scenario` / `Proposal` | Staged changes before commit | approval cards, preview, task graph |
| `DecisionLineage` | Data/version/agent/app/approval chain | journal + ontology projection |

### 11.2 Target chain

```text
Goal / Task
  -> Decision (question, criteria, context)
  -> Options (considered, rejected, why)
  -> ActionType (typed verb, permission, approval)
  -> ActionInvocation (policy, approval, execution)
  -> Outcome (verification, artifact, state)
  -> DecisionLineage (data version, run, agent, app, time)
```

`journal` remains the source of truth. The ontology is a deterministic,
permission-aware projection; P0 must not change runtime behavior.

### 11.3 Phases

#### P0 — read-only decision/action export (1.1, ~3 weeks)

Status: **first slice implemented (2026-11-19)** — `Decision`, `Outcome`,
`Option` and `Criterion` nodes, IDs, types, bindings and validation are live;
the standalone ActionType registry and ToolSpec/CapabilityManifest generation
are also live. `Scenario` remains.

- Add `Decision`, `Option`, `Criterion`, `ActionType`, `ActionInvocation`,
  `PolicyDecision`, `Approval`, `Outcome`, `Scenario` to the 1AO type registry.
- Derive decision/action lineage from existing journal, answer, action log and
  session data; unknown fields are explicit `Unknown`, never fabricated.
- Add decision/action competency questions and golden JSON-LD tests.
- No prompt, journal event or answer schema change.
- Acceptance: 6 decision/action CQs answerable; deterministic export; redaction
  tests pass; `verify.sh` green.

#### P1 — Action Registry + typed tools (1.2, ~6 weeks)

Status: **code-release vertical implemented locally (2026-11-19)** — the standalone
`ontology/actions.json` defines four code-change/release actions;
`ontology actions` lists them; each action can generate a ToolSpec and
CapabilityManifest. `code.propose_change` is registered as
`code_propose_change`, writes a 0600 proposal artifact through ExecutionGate,
and exports ActionInvocation/Decision.hasAction plus a read-only Proposal node.
`code.run_checks` writes a 0600 check report with per-file SHA-256; missing or
oversized paths fail. `code.prepare_release` requires an approved receipt and a
passed check report, then writes a local release manifest and SHA256SUMS; it
does not build/package or publish. `code.approve_change` is a CLI/library
receipt (`action approve-change`), not a model tool, so the agent cannot
self-approve.

P1 hardening gate: **green (2026-11-19)** — negative tests for read-only,
path traversal/symlink, corrupt proposal, stale approval, tampered check report
and missing approval pass; proposal/receipt/report/release carry
`action_version`; action capability manifests resolve `code.propose_change`.
Action tools are now model-visible only when the capability preflight selects
their manifest; hidden actions are also denied by `request_tools` and by the
runtime executor (`capability_not_selected`). Human approval is available
through `1agent action list|approve|deny` and
`1agent action approve-change`; the TUI approval queue is not yet built.
Remaining P2/P3: Scenario merge, object/action policy and Ontology MCP. See
§11.6.

- Define `ActionType` schema (JSON Schema parameters, preconditions, submission
  criteria, risk/reversibility, approval policy, side effects, postconditions,
  idempotency key).
- Implement 3–5 reference actions in one vertical (chosen: code-change/release
  with `ProposeChange`, `RunChecks`, `ApproveChange`, `PrepareRelease`).
- Generate `ToolSpec`/`CapabilityManifest` from ActionTypes; the model sees one
  typed tool per write action, while reads collapse into query/search tools.
- Gate invocation on existing Authority/Policy/Approval; record
  `ActionInvocation -> Decision -> Outcome`.
- Acceptance: undeclared actions cannot be invoked; denied actions leave no side
  effects; capability compiler selects typed actions; action lineage complete.

#### P2 — Scenario / Proposal staging (1.2, ~4 weeks)

- Agent stages actions into a sandbox scenario; human reviews diff/impact.
- Merge is a single approved transaction with postconditions.
- Rejection leaves production untouched.
- Acceptance: no production mutation before approval; atomic merge; rollback
  test passes.

#### P3 — Object/action policy + Ontology MCP (1.3, ~6 weeks)

- Extend `AuthorityProfile`/`PolicyRequest` with object-type/action scopes;
  tool access depends on access to the underlying object.
- Expose 1Agent's object reads, query functions and ActionTypes as MCP tools
  (reads consolidated, writes one tool per action), with OAuth/scopes and
  journaled lineage.
- Acceptance: tool denied without object access; MCP clients see typed actions;
  every external action writes decision lineage.

### 11.4 Reference vertical

Pick one vertical slice before P1; do not build a generic ontology platform.
Recommended candidates:

1. **Document review/publish**: `ReviewDocument`, `ApproveDocument`,
   `PublishDocument`, `RequestChanges`.
2. **Code change/release**: `ProposeChange`, `RunChecks`, `ApproveRelease`,
   `PublishRelease`.

Each action type must have an oracle/verification path and an approval policy.
The reference vertical also becomes a 1ASH task family, so the harness and the
ontology validate each other without circular self-scoring.

### 11.5 Non-goals and risks

Non-goals: OWL reasoner, full Palantir clone, full enterprise RBAC, graph
database migration, automatic ontology extraction from LLM output.

| Risk | Mitigation |
|---|---|
| Ontology theater (graph without actions) | P1 must ship real typed actions, not just RDF |
| Action/tool explosion | Capability compiler + app/action scopes; expose a small selected set |
| Policy complexity | Start with object-type + action scopes; add property/cell later |
| Model/tool drift | Generate tool specs from ActionType; golden tests |
| Decision data privacy | Redact options/evidence; retention and access policy |
| Scope creep into 1.1 | P0 only in 1.1; P1–P3 in 1.2/1.3 |

### 11.6 Delivery sequence and release boundary (2026-11-19)

Do not mix the 1.0 release candidate with 1.1 action/ontology features.

| Line | Contents | Rule |
|---|---|---|
| `release/1.0` | rc.12 + safe redundancy cleanup + T7 QA | No 1AO/1ASH feature commits; external gates still apply |
| `1.1-dev` | 1AO-P + 1ASH | 1.1 only; no "1.0 GA" claim |

Order (do not start a later item before its gate):

| Step | Work | Gate / acceptance |
|---|---|---|
| 1. P1 hardening (~1 week) — **gate green** | Negative tests for read-only, path traversal/symlink, oversized/ corrupt proposal, wrong/stale approval, check-report mismatch, double decision; add `action_version` to proposal/receipt/release; capability manifests for typed actions | Every bad path fails closed; undeclared/unselected actions are not model-visible; `verify.sh` green |
| 2. 1ASH M0/M1 (parallel, ~3 weeks) | Freeze task/run/trace/report schemas; Inspect runner; one coding + one artifact task | oracle passes, no-op fails, `1ash verify` reproduces the report |
| 3. Scenario merge (~2–3 weeks, only after step 1) | Add change payload (`patch`/worktree), run checks on the staged tree, bind approval to proposal+patch SHA, atomic merge and rollback | No target mutation before approval; failed merge leaves no partial state; merge receipt + re-checks |
| 4. Object/action policy (~2 weeks) | Action scope + object-type scope in Authority/Policy; tool access depends on object access | Denied action has no side effect; policy decision is journaled |
| 5. Ontology MCP (~2–3 weeks) | Reads as query tools; writes one typed tool per ActionType; external agents cannot bypass human approval | MCP client denied without scope; every external action writes lineage |
| 6. 1ASH task suite + pilot (~4–6 weeks) | 30 tasks (20 public/10 private), six families; external pilot rerun | ABC checklist, oracle/no-op, deterministic rerun, external report |

Immediate two weeks:

1. Branch `release/1.0` from the rc.12 line; keep 1.1 work on `1.1-dev`.
2. Finish P1 negative tests and action versioning.
3. Freeze 1ASH schemas (M0) and start the Inspect runner (M1).
4. Do **not** start Scenario merge until the P1 negative-test gate is green.

Not now: public leaderboard, multi-vendor judge platform, full object-level
RBAC, Ontology MCP before policy, Scenario merge before negative tests, and any
claim that a local release manifest is a built/published artifact.

## 12. Non-goals and open decisions

Non-goals: public leaderboard, multi-vendor marketplace, full benchmark
reimplementation, OS sandbox, mobile, "AGI score".

Open decisions before M1:

- Working name/licence: keep `1ASH` proprietary or publish schemas under an
  open licence?
- Private holdout custody: internal only, or an external reviewer?
- Pilot partners: which 2–3 teams can run the package?
- Judge: local model or provider model; calibration sample size.
- A2A remote mode in v0 or v1.
- Human calibration budget (100 vs 300 samples).
- 1AO-P reference vertical: document review/publish or code change/release.
- `Decision` first-class in P0, or derived from `Answer` and promoted in P1.1?
- ActionType source: derive from existing ActionCard/CuaAction, or maintain a
  standalone registry with code generation?
