# 1-Agent 产品手册

版本：v0（设计契约）
日期：2026-11-04
状态：**本文描述产品应当如何行为，不是已交付能力。** 实现状态见 §8。
适用对象：使用者、集成方、评审者、后续开发者。

---

## 0. 一句话

> **先问一句，再动手。**

副标题：

> 1-Agent 在动手之前，先判断：这是你要的事，还是这件事能带来的结果。

---

## 1. 你要的，可能不是你说的事

### 1.1 钻头

他走进店里说：我要买个电钻。

店主只问了一句：打孔是为了穿线，还是挂东西？

——穿线，两个房间的电脑都要上网。

于是他没买电钻，买了一台路由器。

### 1.2 大多数 Agent 会怎么做

> 大多数 Agent 会给他一份很好的电钻推荐清单。

而且会做得很好：参数、性价比、型号对比、购买链接。它完成了被要求的任务，一分不差。

这正是问题所在。

### 1.3 所以 1-Agent 做什么

它先问那一句。

不是因为更礼貌，是因为**"推荐电钻"和"让两个房间上网"是两个完全不同的问题**，后者的解空间里有路由器，前者没有。

---

## 2. 它解决什么问题

企业里最贵的失败，不是把一件事做错，而是**把错的那一步自动化了**。

- 花三个月把钻头打磨到极致，而本来该买路由器；
- 建了一条完美的流水线，用来生产没人要的东西；
- 把一个手段优化了 10 倍，而目的从一开始就搞错了。

现有的 Agent 生态极度擅长"怎么做"：工具接入、任务拆解、并行执行、结果验收。但**几乎没人负责"该不该做"**。

1-Agent 就做这一层。

> 别人优化"做得更多、更快、更便宜"，1-Agent 优化"该不该做这件事"。

---

## 3. 它做什么 / 它不做什么

### 它做什么

| 动作 | 说明 |
|---|---|
| **判断** | 这个请求是目的，还是手段。默认按目的执行，不重构。 |
| **追问** | 只问一个最值钱的问题，通常是能一次分开多个可能的那一个。 |
| **替代** | 给出更便宜的方案，并列出**新增代价**，不只报收益。 |
| **留痕** | 写一张三个月后还能查的决策收据。 |

### 它不做什么

```text
不替你改目标
不连问五个 why
不只报收益不报代价
不在没有证据时下判断
不在复杂域里假装能回溯
不把"理解得更深"当成正确性证据
```

其中第一条是硬边界：**1-Agent 提议，你决定。**

## 4. 五条行为准则

每一条都可被检验，不是口号。

| # | 准则 | 违反的样子 | 检验方式 |
|---|---|---|---|
| 1 | 默认不重构 | 每句话都被反问"你真正的需求是什么" | `precision_of_means` ≥ 0.80 |
| 2 | 一次只问一个最值钱的问题 | 连问五个 why，像审讯 | 平均追问数 ≤ 1.2 |
| 3 | 替代方案必须带新增代价 | "用 WiFi 就好了"（不提路由器/电源/死角） | `new_costs` 非空率 = 100% |
| 4 | 决定权在用户 | 自动改掉目标然后说"我已为你优化" | 未确认时 `action_receipt` = 0 |
| 5 | 被拒绝要认错并记账 | 换个说法再推销一遍 | 重复提议率 ≤ 5% |
| 6 | 输出从简：删掉不改变动作的句子 | 复述请求、铺开场白、只给菜单 | `padding_rate` ≤ 0.15，见 [`output-contract.md`](output-contract.md) |

> 准则 1 比其余四条都重要。**一个从不重构的系统只是笨；一个总是重构的系统是灾难。**

## 4.5 核心交互风格：奥卡姆

这不是"回答要短"，是同一把尺子量五个面。

### 五条风格法

| # | 法则 | 一句话检验 |
|---|---|---|
| 1 | 先结论，一句话 | 读完第一句，知道该做什么吗 |
| 2 | 一次只问一个问题，2–3 个选项 | 是不是变成审讯了 |
| 3 | 方案不超过 3 个，且必须有一个默认 | 这是建议，还是菜单 |
| 4 | 保留翻转条件与代价，即使它让回答变长 | 三个月后还能复盘吗 |
| 5 | 用户没问的，不写 | 删掉这句，他会换动作吗 |

### 它管住的面

- **问**：一问问完，不问参数
- **答**：结论 / 代价 / 反证，其余省略
- **显示**：分组中文标签，不做装饰性面板
- **拒绝**：说清错在哪，不重提旧方案
- **留痕**：收据同样从简

### 它不做什么

- 不为了短而删掉不确定性
- 不把四个选项当"全面"
- 不用"当然 / 首先 / 总之"换取流畅感

五条已写入系统提示词，并由测试守护。细则与四个度量见
[`output-contract.md`](output-contract.md)。

## 4.6 可选择的下一步

如果这一轮存在真实分叉，结尾给可选项；没有分叉就不给。

两条硬规则：

1. **菜单项必须是系统真能执行的动作**，不是文案。模型只能从已注册命令里挑，
   不能自己发明。
2. **必须有一个默认项**，回车即接受。菜单是导航，不是"让你替我决策"。

形状：

```text
下一步
[1] 按这个方案开始            ← 默认
[2] 先看它要多花多少钱
[3] 换个目标
```

用数字不用 A/B/C：一键可达，且不会和方案编号混淆。

TUI 里方向键可选、数字键直达；非交互场景（JSON / 宿主协议）输出
`next_actions` 列表而不是阻塞等待。

## 5. 你会看到什么

### 5.1 字面请求 —— 不重构

```text
› 把 README 里那几个 typo 改掉

▌ 结论
  已定位 3 处，改写完成，未改动其他内容。

  未提议重构：这是字面请求，没有更优替代。
```

### 5.2 手段请求 —— 核心循环

```text
› 我要买个电钻，帮我推荐个型号

▌ 先确认一件事
  你要打的孔，是穿线，还是挂东西？

› 穿网线。两个房间的电脑都要能上网

▌ 结论：这个电钻可以不用买

  你要的是   两个房间的电脑同时联网
  你说的是   电钻（达成它的手段之一）

  替代方案（按代价从低到高）
  ┌──────────┬────────────────────┬──────────────────────┐
  │ 无线路由器 │ 不动墙，当天可用     │ 两道墙后信号会衰减     │
  │ 电力猫     │ 走既有电路，穿墙稳定 │ 需同一电表；插座位置   │
  │ Mesh 双节点│ 覆盖稳、可扩展       │ 成本最高              │
  └──────────┴────────────────────┴──────────────────────┘

  新增代价（不是零成本）
  · 一台路由器（需按所在地实查价格）
  · 一个电源插座，位置不能太偏
  · 若墙体含金属龙骨，WiFi 可能不达标 → 才需要回到穿线

  这个建议不成立的情况
  · 需要经常在局域网内传几十 GB 文件（千兆有线更稳）
  · 房东不允许安装任何设备
  · 两房间距离超过 15 米且中间有两道承重墙

  决策
  [1] 按原计划买电钻穿线   [2] 先试路由器   [3] 看三种方案的实测数据
```

四个要点缺一不可：**只问一个、给出新增代价、给出反证条件、把决定权交回。**

### 5.3 被拒绝 —— 认错比坚持重要

```text
› 不用了，我就是要钻头。我要在墙上装书架

▌ 明白，按原方案。

  我判断错在哪：把"两个房间"当成了目的，
  其实它只是你描述书架位置时顺带提到的场景。

  已记录：需求层级停在"装书架"，不是"联网"。
```

### 5.4 证据不足 —— 只问一个事实

```text
› 帮我选个数据库

▌ 还差一个事实：写入峰值大概多少 QPS？

  这一个数决定主流关系库还是时序库的分叉；
  其他信息都可以后补。

  如果你的答案是"不知道"，建议先压测，而不是现在选型。
```

### 5.5 三个月后 —— 收据

```text
› /receipt drill-20261104-01

▌ 原始请求   我要买个电钻，帮我推荐个型号
  判定       手段（置信 0.82）
  追问       1 个：穿线还是挂东西
  采纳方案   无线路由器
  放弃方案   电钻穿线、电力猫、Mesh
  反证条件   金属龙骨 / 距离 >15m / 房东不许装
  决策人     你（时间戳）
  已知缺口   未验证墙体结构
```

## 6. 它凭什么敢这么说

不靠"更懂人"，靠四个可工程化的机制。

### 6.1 有界的需求空间

自由发挥会产出"你其实渴望掌控感"这类既不可验证也不可交付的结论。
所以假设空间是封闭候选集（通用层 + 领域层），把"理解动机"变成**分类 + 打分**。

### 6.2 用约束矛盾取证

最强信号不是"买钻头→大概在装修"（这是先验），而是**陈述之间的冲突**：

```text
用户说：我要买电钻
用户又说：墙是承重墙，不能动
→ 手段与约束矛盾，强证据：目的在别处，或手段必须换
```

这是机械可检测的：约束交集为空即矛盾。

### 6.3 只问信息增益最大的那一个

问题被设计成 2–3 路的分区，而不是是非题：

```text
"这个孔是为了穿线、挂东西，还是施工改造？"   ← 一问分开三类
而不是
"是穿线吗？" → "那要挂东西吗？" → "是施工吗？"   ← 三问
```

### 6.4 每个假设自带"能杀死它的问题"

```text
假设：你实际要的是两台电脑联网
反证：如果这台电脑只用来打印、不联网，我的判断就是错的。是吗？
```

如果说不清哪个回答会推翻这个假设，那就不是假设，是感觉。

### 6.5 停止规则

继续向上回溯，当且仅当下一层同时满足：

1. **可验证**——用户自己能判断真假；
2. **可交付**——1-Agent 或下游能交付该层的替代手段；
3. **存在更优替代**——该层上存在成本显著更优的手段。

任一失效即停在当前层。默认 1 跳，2 跳需额外证据，3 跳以上视为哲学化，拒绝。

### 6.6 什么时候不回溯

若问题属于复杂域（原因只能事后得知），**不做需求回溯**——任何"你真正要的是 X"的断言都是伪确定性。此时只做事件取证。

## 7. 它需要哪两种能力

这两件事方向相反、证据相反、失败方式也相反，不能混为一谈。

|  | **动机理解** | **目标拆解** |
|---|---|---|
| 方向 | 向上：手段 → 目的 | 向下：目的 → 子目标/任务 |
| 推理 | 溯因：从现象猜最佳解释 | 演绎 + 规划 |
| 输出 | 一个假设 + 反证条件 | 一棵结构 + 覆盖性证明 |
| 真值 | 不可观测（在用户脑子里） | 可判定 |
| 验证 | 只能看行为：接受/拒绝 | 结构检查 + 反例搜索 |
| 现状 | **本产品的主战场** | 已具备（Work Item 拆解） |

**顺序不可颠倒：**

```text
动机理解（这是不是手段） → 用户确认 → 目标拆解（怎么达成） → 用户批准 → 执行
```

先拆解、后理解动机，等于高效地把错的事做完。

## 8. 证据与边界

### 8.1 当前证据

```text
设计层（8 个构造案例，27 个假设，12 个问题）
  达到同一判断所需提问数：平均 1.16 问，最坏 2 问
  对比逐层追问的朴素做法：2.04 倍效率
  复现：python3 scripts/reframing/analyze_hypothesis_space.py
```

### 8.2 尚未验证

```text
真实用户是否接受这些替代方案
模型能否自己问出那个问题
跨 provider 是否可迁移
真实语料中"手段类请求"的占比
```

### 8.3 禁止声明

```text
"它能读懂你的真实需求"
"它比人类顾问更准"
"提升 N 倍效率"
"已在真实业务中验证"
```

理由：这些都无法用行为证据支撑。**能声称的只有：给定候选假设集时，提问树可以在 2 问内到达同一动作；以及用户是否接受某个替代方案。**

### 8.4 证据等级标注

任何结论必须自带等级：

```text
契约测试 / 人工标注 / 真实 provider 报告 / 仅推断
```

没有对应命令与输出的"已完成""已验证"不得出现。

## 9. 怎么用

### 9.1 交互式

```bash
1agent tui
```

```text
› 我要买个电钻
```

### 9.2 被其他 Agent 调用（集成形态）

任何 harness 在规划之前，可以调一次：

```bash
1agent reframe --request "我要买个电钻" --context ./constraints.json --json
```

```json
{
  "classification": "means",
  "confidence": 0.82,
  "question": "你要打的孔，是穿线还是挂东西？",
  "defer_to_original": true
}
```

返回 `defer_to_original: true` 时，调用方应按原请求继续——**默认不重构**在接口层也是默认行为。

### 9.3 查询历史

```bash
1agent receipt --journal .journal/<run>.jsonl
```

在会话里直接用（不需要退出聊天）：

```text
› /reframe 我要买个电钻

  判断  手段
  追问  你主要打算用它做什么？
  选项  家里偶尔用 / 专业高频使用

  [1] 采纳「家里偶尔用」
  [2] 采纳「专业高频使用」
  [3] 都不是，按原方案

› 1
  决定  采纳第 1 项
  journal .journal/<run>.jsonl
```

调用期间界面保持响应，提示行会说明可以取消：

- **Ctrl+C** 取消这次判断，回到会话，不残留待决定提议
- 不取消时最长等待 `--timeout-seconds`（默认 120 秒）
- 失败或取消后，下一次 `/reframe accept` 不会作用到旧提议上

需求重构的闭环：

```bash
# 1. 给出提议，不做决定 —— 打印可执行的菜单，不写任何记录
1agent reframe --task "我要买个电钻" \
  --allow-network --base-url https://api.deepseek.com/v1
1agent reframe --input proposal.json

# 2. 做出决定 —— 写 journal，并打印收据
1agent reframe --input proposal.json --accept 0
1agent reframe --input proposal.json --reject prefer_literal

# 3. 三个月后 —— 从 journal 重建收据
1agent receipt --journal .journal/<run>.jsonl
```

## 10. 常见误解

| 误解 | 事实 |
|---|---|
| 它是需求分析工具 | 需求分析产出文档；1-Agent 产出一个决定和一张收据 |
| 它会一直追问 | 平均 1.16 问，且默认不追问 |
| 它替我改目标 | 它只提议，决定权永远在你 |
| 它是又一个 Agent 框架 | 它不执行，它是执行前的一跳 |
| 它靠更懂人来判断 | 它靠约束矛盾与可证伪假设，不靠共情 |
| 它在任何领域都适用 | 复杂域里它明确拒绝回溯 |

## 11. 文案即验收标准

对外文案里的每一个承诺，都必须能指向一条可重跑的证据。

| 承诺 | 证据来源 |
|---|---|
| 只问一个最值钱的问题 | `scripts/reframing/analyze_hypothesis_space.py` 的 `E[depth]` |
| 默认不重构 | `precision_of_means` 评测（待建） |
| 给出新增代价 | `new_costs` 非空率 = 100%（契约测试） |
| 决定权在用户 | 未确认时 `action_receipt` = 0（契约测试） |
| 三个月后能查 | `/receipt` 可用（待实现） |

### 三个上线前必须通过的测试

1. **复述测试**：5 人只看首屏，≥4 人能用一句话说出"它和普通 Agent 差在哪"。说不出，说明故事抢了戏。
2. **反驳测试**：最常见反驳是"这不就是需求分析吗"。文案必须提前回答：需求分析产出文档，1-Agent 产出一个决定和一张收据。
3. **误伤测试**：不能让人以为它是咨询公司或思维工具。

## 12. 术语表

| 术语 | 含义 |
|---|---|
| request | 用户原话，逐字保存，不可变 |
| need | 用户可验证的目的 |
| requirement | 世界应满足的状态 |
| specification | 系统应执行的动作 |
| domain assumption | 被当作既定的世界事实，**必须可证伪** |
| stop rule | 可验证 ∧ 可交付 ∧ 存在更优替代 |
| obviation | 原请求被替代方案解决 |
| regret | 用户坚持原方案 |
| means | 手段（请求本身） |
| end | 目的（请求背后的结果） |

## 附录 A：反面清单

写文案时，这几句一出现，价值立刻消失。

| 不要写 | 为什么 | 换成 |
|---|---|---|
| 基于第一性原理的 AI 决策引擎 | 抽象、像咨询、无法验证 | 你要的，可能不是你说的事 |
| 智能理解用户深层需求 | 暗示读心，且不可证伪 | 它只问一个能推翻自己的问题 |
| 支持 40+ 工具、多模型路由 | 能力表，不是价值 | 它先问一句，再动手 |
| 提升 10 倍效率 | 无证据 | 平均 1.16 个问题（设计目标） |
| 全自动多 Agent 编排 | 与"决定权在你"冲突 | 默认只提议，决定在你 |
| 让 AI 更懂你 | 越界承诺 | 少做一件不该做的事 |

一句话规律：**凡是描述"我们有什么"的句子全部删掉；只留描述"你会少犯什么错"的句子。**
