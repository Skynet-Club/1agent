# 会话交互设计（0.98）

Date: 2026-11-15  
Status: P0/P1 + UI-level pause + Agent-分队 v1 implemented; multi-session P2 designed only  
Scope: 1Agent TUI 的会话切换、追问、中断/恢复与运行中队列

这份文档定义「像 agent 一样工作」的第一层交互，也为后续 Super-Agent
的多会话/多任务界面留出边界。原则只有四条：

1. **随时知道自己在哪个会话**：标题、ID、最近修改时间、最近状态可见。
2. **追问不断线**：切换会话后仍能接着上一次工作继续，不要求用户复述。
3. **控制权在用户手里**：中断、恢复、归档、删除都要有明确反馈和可逆路径。
4. **审计不丢**：所有切换、重命名、归档、中断都保留 journal 与会话记录。

## 1. 当前能力与限制

| 能力 | 现状 |
|---|---|
| 会话存储 | `journals/.sessions/<id>/session.json`，含标题、journals、workspace、归档状态 |
| 恢复会话 | 切换时按 journal 顺序 replay，恢复完整可见历史 |
| 追问 | 新一轮任务注入最近 6 轮上下文（请求、结论、状态、最多 3 条 claim、3 条 evidence、4 条工具结果，总计 ≤12k 字符） |
| 运行中追问 | 输入进入队列，当前运行结束后按顺序自动提交；`↑` 可取回编辑 |
| 暂停 | 运行中第一次 `Esc` 暂停，`Enter` 继续；暂停时状态保留、journal 不终止 |
| 中断 | 暂停时第二次 `Esc`，或运行中 `Ctrl+C`，取消当前运行并保留 journal |
| 恢复 | `Ctrl+R` 从最后一个 checkpoint 生成恢复点并继续；没有 checkpoint 时明确拒绝 |
| 后台多会话 | 未实现。当前一次只有一个活动运行；Super-Agent 阶段再做 |

## 2. 键位

### 2.1 主界面

| 键 | 行为 |
|---|---|
| `←`（输入框为空） | 打开会话选择器 |
| `←`（输入框有内容） | 正常移动光标，不打开选择器 |
| `↑` / `↓`（输入框为空） | 历史输入；运行中且队列非空时 `↑` 取回排队消息 |
| `Enter` | 提交任务；运行中则把当前输入加入队列 |
| `Enter`（运行中暂停时） | 继续运行 |
| `Esc`（运行中第一次） | 暂停 |
| `Esc`（暂停时第二次） | 中断 |
| `Ctrl+C` | 有选中文本时复制；否则中断当前运行 |
| `Ctrl+R`（空闲） | 恢复上一次中断的运行 |
| `Ctrl+K` | 命令面板（既有行为） |
| `Ctrl+G` | 打开 `分队 Agents` 页签（运行中也可打开，只读） |
| `Ctrl+O` | 运行详情（既有行为） |
| `Ctrl+Tab` | 切换模式（既有行为） |
| `Ctrl+Q` | 退出；第一次提示确认，第二次退出 |

### 2.2 会话选择器

| 键 | 行为 |
|---|---|
| `↑` / `↓` | 选择会话 |
| `PageUp` / `PageDown` | 快速移动 8 行 |
| `Home` / `End` | 第一个 / 最后一个 |
| `Enter` / `→` | 切换并恢复该会话 |
| 选中行 | 右侧自动预览最近一次任务、结论、证据（无需按键） |
| `n` | 新建会话并切换 |
| `/` | 搜索标题、ID、workspace |
| `Ctrl+R` | 重命名当前选中的会话 |
| `Ctrl+D` | 归档 / 取消归档；需要再按一次确认 |
| `Ctrl+A` | 显示 / 隐藏已归档会话 |
| `Esc` / `←` | 关闭选择器 |

规则：

- 会话行显示最近修改时间 `YYYY-MM-DD HH:MM`（不含秒），不再显示被截断的运行次数。
- 当前会话不可归档，避免把正在使用的上下文藏起来。
- 归档可逆；删除仍走 `/session delete <id> confirm <id>`。
- 预览只读最近一条 journal，不展示密钥或工具原始输出；↑↓ 改变选中行时右侧直接刷新。
- 切换会话会关闭选择器、恢复 transcript，并提示「继续输入即可追问；← 打开会话列表」。

## 3. 追问语义

追问不是把整段聊天记录原样塞回模型，而是构造一个**有界的会话事实包**：

```text
Previous user request: ...
Previous answer conclusion: ...
Previous answer status: 完成 / 需证据 / 有条件 / ...
Previous claim (实测): ...
Previous evidence (path): ...
Previous tool result (read_file / Ok): ...
```

约束：

- 最多最近 6 轮，总计 ≤12,000 字符，单条 ≤1,600 字符。
- 如果有覆盖全部 journal 的 compaction summary，只注入摘要。
- 工具结果最多每轮 4 条，避免旧输出淹没当前任务。
- 这些事实是「上下文」，不是「当前证据」；模型必须重新验证会变化的事实。

## 4. 暂停、中断与恢复

### 4.1 用户看到的

```text
已暂停 · Enter 继续 · 再按 Esc 中断
```

- 运行中第一次 `Esc`：暂停。状态栏显示 `⏸ 已暂停`，活动卡片保留。
- 暂停时 `Enter`：继续运行；再按 `Esc`：中断。
- 中断后输入框恢复空闲，可以继续输入新任务或按 `Ctrl+R`。

```text
已中断 · journal 已保存 · Ctrl+R 恢复本次运行
```

- 没有 checkpoint 时显示「这次中断没有可恢复的 checkpoint」，不假装成功。
- 恢复时显示恢复点路径；恢复运行会生成新的 `resume-<uuid>.jsonl`，原 journal 不修改。

### 4.2 暂停机制（UI 层）

暂停不是取消，也不生成恢复点：

1. TUI 把状态置为 `Paused`，并停止轮询 `runtime.run` 的 future。
2. 运行时 future 停在最近一个 await 点，内存状态、消息历史和 journal 都保留；
   journal 不会写入终止事件。
3. `Enter` 清除 `Paused` 并恢复轮询；运行从暂停点继续，不重放已完成步骤。
4. 暂停时间从 UI 的运行计时中扣除，但**仍会计入任务/provider 自身的超时**。

边界：

- 暂停发生在 UI 调度层，不是 runtime 的步骤状态机；已经在执行的阻塞工具或
  外部请求可能继续完成，只是结果暂不推进 agent loop。
- 进程崩溃会丢失内存中的暂停状态；此时只能按 journal 的 checkpoint 恢复。
- 暂停时间过长可能触发 provider/任务超时，UI 会在恢复时收到超时错误。

### 4.3 中断与恢复机制

1. 用户第二次 `Esc`（或 `Ctrl+C`）取消 `CancellationToken`。
2. runtime 写入终止事件，原 journal 进入 terminal 状态。
3. `resumable_journal_prefix` 找到最后一个 `Checkpoint` / `CheckpointDelta`，复制到该点为止的事件，生成恢复点。
4. `runtime.resume` 从恢复点继续；恢复点必须通过工具配对校验。
5. 成功后把恢复点记录进当前会话；失败时保留原 journal 并报告原因。

中断走的是「终止 + checkpoint 恢复」，与暂停不同：进程内状态不保留，恢复
依赖 journal 中最后一个 checkpoint。

**副作用边界**：恢复点是最后一个 checkpoint。如果中断发生在工具调用执行中，
恢复可能重试该工具；不可逆外部操作（付款、发信、远程写入）不能依赖 `Ctrl+R`
保证只执行一次，必须由工具自身的幂等键兜底。

## 5. 运行中队列

- 运行中输入的字符正常编辑输入框；`Enter` 把内容加入队列，不打断当前运行。
- 队列按 FIFO 在当前运行结束后自动提交；当前运行结束后若输入框为空，下一条自动进入。
- 暂停时 `Enter` 表示继续运行，不会把输入入队；需要排队时先继续或中断。
- `↑` 在输入框为空时取回最近一条排队消息，编辑后再次 `Enter` 重新排队。
- 有 pending 确认、clarify、命令面板或会话选择器打开时，不自动提交队列，避免绕过安全确认。
- 队列属于当前会话；切换会话或 `/clear` 会清空队列。

## 6. 与 Claude Code / OpenCode 的取舍

| 产品 | 机制 | 我们采用 / 不采用 |
|---|---|---|
| Claude Code | 空输入框 `←` 进入 agent view；`Space` peek+回复；后台会话继续跑 | 采用「空输入框左键」和自动预览，暂不做后台多会话 |
| Claude Code | 运行中输入 Enter 入队，`↑` 编辑，`Ctrl+Enter` 立即发送 | 采用入队与 `↑` 编辑；暂不做立即发送 |
| OpenCode | leader 键 `Ctrl+X` + `L` 打开会话列表；模态层搜索/改名/删除 | 不引入 leader 键；用左键 + `/session`，保持 1Agent 现有键位 |
| OpenCode | 宽屏可切换常驻侧栏 | 暂不做常驻侧栏，避免挤压 80 列终端和军事绿主界面 |

选择左键而不是 leader 键的理由：左键在空输入框没有编辑语义，冲突最小；
同时保留 `/session` 作为可发现、可脚本化的入口。

## 7. Agent-分队（v1）

命名：整体叫 **分队**，单个子进程叫 **队员**，执行对象叫 **子任务**。

0.98 已有 `spawn_agent`：子进程是另一个 `1agent run`，有独立 journal、
workspace、预算；深度上限 2，扇出上限 8，父子权限取交集，子 journal 会
audit。缺的是可见性。

v1 交互：

- `Ctrl+G` 打开 `分队 Agents` 页签；标题栏为 `Tab：“会话 Sessions | 分队 Agents ”`，`Tab` 切换；`Tab：` 与引号保持黯绿，只有当前标签文字变亮，背景始终不变。
- 队员行显示：状态、子任务、深度 D1/D2、耗时、运行中/已完成/失败/超时。
- 选中行自动刷新右侧预览；预览读子 journal 的事件时间线（任务、工具调用、
  工具结果、结论、结束原因），不是只读 stdout。
- 运行中每 500ms 刷新一次；`Esc` 关闭页签。
- v1 **只读**：不停止、不接管、不修改子进程；生命周期仍由父会话管理。
- 运行中打开页签不允许切换会话；切换会话仍需先暂停/中断。

数据源是 `~/.cache/1agent-tmp/subagents/registry.jsonl`（0600、目录 0700），
由 `spawn_agent` 在启动前写 `starting`，拿到子 PID 后写 `running`，结束写
`completed/failed/timed_out`；guard 被丢弃时写 `cancelled`。记录按
`root_pid` 过滤，避免同一台机器上其他 1agent 进程的队员混进来。登记表是
本地 UI 状态，不是审计证据；子 journal 才是。

v1 限制：

- 父任务 `Esc` 暂停时，已启动的子进程仍会继续运行；页签明确显示父/子状态，
  但不假装父暂停等于子暂停。
- 登记表没有持久化到 session；重启后只能看到仍在缓存中的记录。P2 再把它
  写进 `.sessions/<id>/subagents.json`。
- 不能停止/重试/接管队员；`Ctrl+D` 等破坏性操作不开放。
- 嵌套队员只展示，不做无限树；最多 D2（与 runtime 深度上限一致）。

### 7.1 后续

- v2：停止/重试队员（二次确认）、暂停传播到子进程、登记表持久化、结果回链。
- v3：daemon 化持久队员、跨会话、steering/接管、多人协作。

## 8. Super-Agent 阶段的预留

P2 要解决的是「多个会话同时在跑」：

- 每个会话拥有独立运行句柄、事件通道和停止令牌；
- 选择器显示 `运行中 / 等待输入 / 已完成 / 失败`；
- 选中即预览，`Enter` attach，`←` detach；
- 切换会话不打断后台运行；
- 把 UI 层暂停升级为 runtime 层步骤状态机（暂停期间冻结任务超时，并阻止
  已启动的工具继续产生副作用）。

当前 P0/P1 已经把「选择器状态」「会话预览」「队列」「恢复点」拆成独立模块，
P2 只需要把 `run_tui_task` 的 await 改成后台任务句柄，不需要重写会话存储。
