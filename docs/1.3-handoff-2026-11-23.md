### Acceptance fix

- `src/tools/terminal.rs`: conservative read-only shell classifier;
  `terminal_exec` records `write=true|false`.
- `src/runtime.rs`: the completion gate ignores `terminal_create`,
  `terminal_output`, `terminal_destroy`, and read-only `terminal_exec`; a
  read-only shell check after acceptance no longer clears the receipt.
- `src/tools/acceptance.rs`: independent verifier labels are normalized to
  `verifier:…`; human verification still requires `human:`.
- `src/verification.rs`: criterion matching ignores case and extra whitespace.
- `src/provider.rs`: a later accepted receipt is decisive; every public and
  hidden criterion needs a result; read-only inspection prefers
  `read_file`/`jq`/`rg`/`ls` over interpreters.

Results (`docs/evidence/phase4-acceptance-fix-2026-11-23/`):

- Core 7 status met 18→21/24, model calls 6→5, tool calls 5→3, prompt tokens
  -25%, wall 17.2→16.5s.
- Full status met only 16→17/24; wall +7%.
- Product eval after the fix: 19/24 (79.16%), pass^3 3/8. This is a small-N
  regression signal, not a proven causal regression. Remaining failures are
  answer generation/repair, not acceptance.

### Budget-aware acceptance reserve

- Act runs get one internal step beyond `max_steps` only when side-effect tools
  ran, a verified artifact exists and no accepted receipt does. That step
  advertises only `acceptance_gate` and injects an internal nudge; otherwise the
  loop breaks before calling the model. `StepModelMetrics.max_steps` reports the
  configured budget.
- The step-budget answer now builds its tool-free request from the latest
  messages, so it sees the last tool result (accepted receipt) instead of the
  request that produced the last tool call.
- At the tool budget, a mixed batch containing `acceptance_gate` runs the gate
  alone and journals the other calls as paired `budget_skipped` observations.
- A write after an accepted receipt sets `receipt_invalidated`; the reserve then
  advertises `verify_artifact` and `acceptance_gate` and asks for a fresh
  receipt for the new bytes. The reserve step may spend one provider attempt
  beyond the configured budget.
- A completed delivery with no flip condition gets one runtime flip condition.
- Tests: `step_budget_reserves_one_acceptance_turn`,
  `mixed_budget_batch_runs_only_the_acceptance_gate`,
  `write_after_receipt_gets_a_verify_and_regate_reserve`. Evidence:
  `docs/evidence/answer-reserve-2026-11-23/`.
- Full product eval N=3: **24/24 (100%), pass^3 8/8, pass at least once 8/8**.
  bug-fix-last-index and long-task-plan are both 3/3.

## Auto-drain and fast default (landed)

- CLI `1agent run` enqueues a fast/deferred delivery and drains the queue in
  the same process; the TUI drains at startup and after every run, and enqueues
  its own fast delivery before draining. Receipts remain in
  `~/.1a/acceptance/{queue,done,ledger.jsonl}` and `/status`.
- `AgentRuntime::with_auto_fast(true)` is the default for `1agent run` and the
  TUI. Auto-fast requires all of: Act interaction, Fast task profile, no
  session continuation, empty injected facts, not verify-only/new-version,

  `ONEAGENT_AUTO_FAST=0` keep Core 7/full. Every run journals
  `FastModeSelected {enabled, reason}`; checkpoints store `fast_mode` so a
  resume rebuilds the same tool surface.

  `with_delivery_root`; a broad configured read root (for example
