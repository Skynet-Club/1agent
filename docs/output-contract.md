# 输出契约：奥卡姆剃刀

Date: 2026-11-04
Status: 规则已定，lint 未实现

## 1. 这条规则要防的是什么

不是"话多"，是**用无关内容换取可信感**：复述请求、铺开场白、罗列相关但无用的背景、
给出四个选项却不推荐、结尾再总结一遍。

这些内容有一个共同特征：**删掉之后，用户的下一步动作不变。**

## 2. 三个剃刀，先砍方案再砍文字

| 层 | 规则 | 违反的样子 |
|---|---|---|
| 实体 | 不得凭空增加假设、需求、角色 | 编一个"你真正的需求是自我实现" |
| **方案** | 用最少的步数达成目的；一跳能解决不设计三跳 | 明明换个设备就行，却规划了改造工程 |
| 文字 | 用最少的字承载决定 | 把一句话的结论写成五段 |

方案剃刀优先。一个措辞精炼但需要三步实施的方案，仍然违反本契约。

## 3. 必要性判据

> **删掉这一行，用户的下一步动作会变吗？不变就删。**

这一句替换掉所有"请简洁""避免冗余"之类的不可执行要求。

## 4. 不可删清单

以下四项即使让回答变长也必须保留，因为它们是**决定本身**，不是修饰：

1. **结论**：一句话，含"做什么"。
2. **翻转条件**：什么情况下这个结论是错的。
3. **高影响未知**：可能推翻结论的那一个。
4. **新增代价**：替代方案相对原方案多出来的成本。

删掉它们会得到一份读起来干净、但**不可证伪**的答案。精简的边界是可审计性，
不是字数。

## 5. 固定骨架

```text
结论   做什么，以及为什么够
代价   新增成本，一行
反证   什么情况下不成立，一行
```

其余内容默认省略。用户追问"为什么"之后再展开，不主动展开。

## 6. 禁止项

| 禁止 | 例 |
|---|---|
| 复述请求 | "您希望我推荐一个电钻，我理解您的需求是……" |
| 开场脚手架 | 当然 / 首先 / 让我们 / 以下是 / 希望对你有所帮助 |
| 空洞对冲 | 可能因人而异 / 具体情况具体分析 |
| 只给菜单 | 四个并列选项，没有默认推荐 |
| 重复结论 | 开头说一遍，结尾再总结一遍 |
| 相关但非必要 | 用户没问的背景、历史、行业现状 |

## 7. 可度量的四个指标

| 指标 | 定义 | 门槛 |
|---|---|---|
| `padding_rate` | 删掉后不改变动作的句子占比 | ≤ 0.15 |
| `alternatives` | 并列方案数 | ≤ 3，且必须有一个默认 |
| `restatement` | 结论与请求的连续重叠字符数 | ≤ 8 |
| `scaffolding` | 命中开场词表的次数 | 0 |

## 8. 落地位置

1. **提示词**：`agent_system_prompt()` 已有 "Put the result first. Do not greet or
   repeat the request."，需要补"禁止脚手架、至多 3 个方案且给出默认、不主动展开"。
2. **契约校验**：`AgentAnswer::validate` 可加复述检测与方案数上限——但会改变
   现有行为，需要单独评估，不在本文件范围内。
3. **收据**：`render_receipt` 已按骨架输出，无需改动。
4. **lint**：`scripts/` 下增加一个只读检查，扫描 journal 中的答案，输出四个指标。
   未实现。

## 9. 已知风险

模型极可能把"简洁"执行成"删掉不确定性"：去掉翻转条件、把 `needs_evidence`
写成 `completed`、用肯定语气掩盖缺口。

因此本契约的有效性不取决于提示词写得多好，而取决于**第 7 节的四个指标是否被测**。
在 lint 上线之前，这一条只能算规则，不能算能力。

## 10. 两种菜单不能混

|  | 方案菜单 | 动作菜单 |
|---|---|---|
| 回答什么 | 做哪个方案 | 下一步做什么 |
| 上限 | 3 | 4 |
| 默认项 | 必须 | 必须 |
| 来源 | 模型提议，须过 `validate` | 只从已注册命令中选 |
| 典型失败 | 只给菜单不给建议 | 给出做不到的选项 |

**混用的后果**：用"你想选哪个"逃避给建议。那是把决策成本推回用户，
不是交互设计。

### 硬规则

1. 模型**只能选，不能写**菜单项。动作 id 必须存在于当前 host binding 的
   命令注册表（`tui_commands.rs`），未知 id 丢弃并记 audit。
2. 只有一个动作时不显示菜单，直接做。
3. 同一菜单不重复出现第二次；用户忽略过的项降权。
4. 非交互场景输出 `next_actions: [{id, label, default}]`，不阻塞。
5. 菜单不计入 `padding_rate`，但它自身受"删掉不改变下一步动作就删"约束。

### 三个指标

| 指标 | 定义 | 门槛 |
|---|---|---|
| `menu_taken_rate` | 用户从菜单里选了的比例 | ≥ 0.3 |
| `default_accept_rate` | 默认项被接受的比例 | ≥ 0.5 |
| `dead_item_rate` | 展示过但从未被选中的菜单项占比 | ≤ 0.2 |

`menu_taken_rate` 过低说明菜单在干扰；`dead_item_rate` 过高说明选项是凑数的。
两者都指向同一件事：删。

### 两种菜单的出现时机不同

| | 方案菜单 | 动作菜单 |
|---|---|---|
| 何时出现 | **只在有真实分叉时** | **每轮结束都给** |
| 不给的情况 | 目的类请求、只有一个动作 | 只有一个动作，或用户正在输入 |

动作菜单是导航，不是决策：它不改变这一轮的结论，只缩短下一轮的命令。
"没有分叉就不给菜单"约束的是**方案菜单**，不是导航。

### 决定菜单例外

方案菜单（采纳 / 拒绝）**不设默认项**。

给"是否采纳"配一个默认，等于替用户做了决定，违反 `product-manual.md` §4 的
决策权边界。默认项规则只适用于动作菜单（下一步做什么）。

两条菜单的区别因此是三处：来源、上限、以及**能否有默认**。

|  | 方案菜单 | 动作菜单 |
|---|---|---|
| 默认项 | **禁止** | 必须 |
