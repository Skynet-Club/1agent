## 0. 结论

**建议 Conditional Go，不建议直接按完整版开工。**

- 先做 **P0 语义核心**：Type Registry + Data Binding + 只读导出 + 校验。
- 0.98.2 推荐范围为 **B：核心血缘版**（R1–R5、R7、R9、R8 的 CLI 查询）；
  **R6 动作/安全和 R8 的 TUI 部分建议移到 0.98.3**。
- 如果 owner 坚持完整 A 版（45–50 人日、5 周、2 人），必须同时接受：
  - ActionType/Policy/Approval 的现有数据缺口；
  - TUI/查询范围压缩；
  - 独立评审和 owner 决策不能晚于 G0。
- 如果 0.98.2 开工两周后仍没有明确消费者（审计 CLI、TUI 血缘、外部导出），
  应停在 P0，不继续做 SQLite/GraphQL/OWL。
- 新增 **Track Q（Quality & Latency）** 约 23 人日；与 B 合计 55–61 人日。
  2 人约 6–7 周；只有 2 人时先做 QG0/QG1 + Semantic P0，暂缓 Semantic R8/TUI。

## 2. 0.98.2 方案的优势

1. **方向正确**：Palantir/Fabric/Netflix 都证明“类型 + 绑定 + 动作 + 安全 + 投影”比纯 RDF 词表更可落地；我们把本体做成运营型类型系统，而不是装饰性 OWL。
2. **风险可控**：journal 仍是事实源；只读投影；导出失败不影响运行；不改模型 prompt/answer schema。
3. **可验证**：确定性导出、golden、SHACL、CQ、兼容矩阵；不是“写完就算”。
4. **补的是真缺口**：队员 parent、session fork、action log、read SHA、policy/approval metadata；这些现在只能靠目录/文件名猜。
5. **为 Super-Agent 留接口**：稳定 IRI、alias/merge、bitemporal、commitment 的扩展位已定义。
6. **分阶段**：P0/P1/P2 可独立交付，不必一次上完。

## 4. 解决方案（按优先级）

### S1. 先冻结范围，分版交付

**建议：**

- **0.98.2 = B 核心血缘版**：R1–R5、R7、R9、R8 的 CLI 查询。
- **0.98.3 = 动作/安全 + TUI**：R6、R8 的 TUI 部分。
- 如果 owner 要求完整 A 版，增加 2 周并明确接受 W4/W5/W9 的残余。

**验收：** G0 记录 scope decision；未移出的 Must 不得在版本中静默删除。

### S2. 指定消费者和 owner

- 消费者 1：`docs/evidence`/审计 CLI（CQ1–CQ8）。
- 消费者 2：TUI 会话/分队血缘（CQ4/CQ13，0.98.3）。
- 消费者 3：外部 JSON-LD/PROV 导出（可选）。
- 设 **Ontology Owner**（词表/绑定）和 **Data Owner**（字段/事件），G0 任命。
- 加使用指标：每周 CQ 查询次数、导出次数、失败率；连续 4 周为 0 则停止扩展。

### S3. 用生成/门禁对抗绑定漂移

- 类型注册表尽量从 Rust 结构/事件枚举生成；不能生成的部分人工补，但必须带 owner。
- 每个绑定带 `mappingVersion`、`sourcePath`、`required`。
- CI 门禁：核心类型/属性绑定覆盖 100%；字段变更若无绑定更新则失败。
- 每次导出带 `bindingVersion` 和 registry hash。

### S4. Action/Policy 只做投影，不做第二套策略引擎

- `ActionType` 从 `CuaAction`/`ActionCard` 生成，字段只描述风险/可逆性/权限。
- `PolicyDecision`/`Approval` 能关联就关联；关联不到标 `Unknown`，不猜。
- 不在本体层重新实现 allow/deny；权限仍以 `AuthorityRegistry` 为源。
- 若要完整动作审计，先在 P1 把 policy/approval metadata 写入 ToolObservation/action log；否则 0.98.2 明确“部分可答”。

### S5. 身份先确定性，后实体解析

- Artifact：SHA-256 主身份，路径为属性。
- Session/Run/Claim/Evidence：确定性 IRI 规则（run/seq 前缀）。
- `EntityAlias`/`mergedInto` 先只记录人工合并 provenance；不做模糊/ML 合并。
- PID、标题、路径永不作为身份。
- 同一 artifact 不同路径必须同 IRI；merge 后保留旧 IRI 的 `mergedInto`。

### S6. Bitemporal 只承诺可得的字段

- `recordedAt` 从 journal timestamp 派生；`observedAt` 从 evidence 派生。
- `validFrom/validTo` 只在证据/审批明确时输出；没有就省略，不默认 now。
- 不把“有 journal 时间”说成“完整双时态”。

### S7. 没有校准就不输出 confidence

- `ConfidenceAssertion` 只在有 provider 校准记录/人工标注时输出。
- 否则保留 `claimStatus`（verified/derived/assumed/...），不生成 0.8/0.9 之类数字。
- 文档和 UI 明确“claimStatus 不是概率”。

### S8. 校验分层：内部先跑，SHACL 做发布门

- P0：Rust 内部规则（必填/枚举/引用完整性/SHA/时间）。
- 发布 CI：pyshacl/Jena 跑 SHACL；版本固定，失败只阻塞发布，不阻塞运行。
- 对当前真实数据先跑一次基线，把已知例外写入 `known-exceptions.md`，不静默忽略。

### S9. 查询/UI 后置

- 0.98.2 先做 `ontology query --cq` CLI；SQLite 投影按需构建。
- TUI 只显示“证据完整度/血缘”摘要，不嵌入完整图。
- GraphQL/图数据库不进 0.98.2；有明确路径查询需求再评估。

### S10. 隐私与权限按 allowlist 导出

- 只导出白名单字段：ID、类型、时间、状态、SHA、引用、摘要。
- 不导出原始 prompt、工具全文、页面内容、密钥、完整文件。
- 导出文件 0600；目录 0700；permission-aware export 测试。
- AccessPolicy/Purpose 先映射现有 authority；没有的字段标 `Unknown`，不假装。

### S11. 性能先基准，再承诺

- 用 100 sessions / 1000 runs 做基准；目标：单 session <2s、查询 <500ms（典型）。
- 大 session 用 journal cursor 增量投影；导出可分页/流式。
- 达不到目标就降级为后台导出/缓存，不牺牲正确性。

### S12. 治理与版本

- G0 决定 namespace（`1agent.dev` 或 `urn:1agent:`）。
- 词表 semver；破坏性变更必须 deprecation + migration note。
- 类型/绑定变更走 PR 模板：owner、影响范围、migration、golden diff。
- 每次发布记录 `ontologyVersion`、`bindingVersion`、`registrySha256`。

## 6. 替代方案对比

| 替代 | 优点 | 为什么不是首选 |
|---|---|---|
| 现状 JSON + 手写脚本 | 零新依赖、最快 | 跨会话/跨 Agent 查询反复写；血缘靠猜 |
| 全量 OWL DL + reasoner | 形式语义强、标准互操作 | 开放世界与业务校验冲突；团队/运维成本高 |
| 属性图数据库 | 路径查询强 | 多一套存储/一致性；当前 CQ 用 SQLite 足够 |
| LLM 自动抽取 KG | 上手快、覆盖非结构化 | 幻觉、不可审计；只能做候选 |
| 只做 A2A/OTel | 对外互操作 | 不解决内部 claim/evidence/action 血缘 |

## 7. Kill criteria（什么时候停）

出现以下任一情况，停止扩展，写清残余：

1. P0 完成后 4 周内无真实消费者使用 CQ/导出。
2. 核心绑定覆盖率无法稳定 ≥95%，且修复成本超过 2 人周。
3. Action/Policy 数据缺口导致 R6 只能大面积标 `Unknown`，且 owner 不愿补 journal/metadata。
4. SHACL/导出性能无法达到单 session 2s，且增量投影也无效。
5. 0.98.0/0.98.1 基线持续漂移，schema 无法冻结。
6. 独立评审提出 P0 级隐私/安全问题，未修复。
