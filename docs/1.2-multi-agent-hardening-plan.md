## 4. Ollama 本地多 Agent 测试

目标：用本地模型验证**协作机制**（spawn、血缘、journal audit、失败/超时、
结果回传），不把本地 8B 的质量当作 M1/发布质量。

### 4.1 部署

上次证据：`docs/evidence/m1-8h-ollama-2026-11-14/`，模型 `qwen3-8b-16k`，
`http://127.0.0.1:11434/v1`，Ollama 从 `/tmp` 启动、非 systemd。

本次使用：

```bash
# 发行包（带 SHA-256 经 skyget 下载）
skyget --json get \
  https://github.com/ollama/ollama/releases/download/v0.40.16/ollama-linux-amd64.tar.zst \
  -o "$HOME/.local/share/1agent-ollama/download" \
  --sha256 87bfafb2acbc89b2e6a1be0a9043de6aa75fb450696f86bc426e65fc448f788d \
  --as claude --detach

# 解压到独立目录（下载物不直接执行）
mkdir -p "$HOME/.local/share/1agent-ollama/dist"
tar --zstd -xf "$HOME/.local/share/1agent-ollama/download/ollama-linux-amd64.tar.zst" \
  -C "$HOME/.local/share/1agent-ollama/dist"

# 启动（nohup，非 systemd；记录 pid）
OLLAMA_HOST=127.0.0.1:11434 \
OLLAMA_MODELS="$HOME/.local/share/1agent-ollama/models" \
nohup "$HOME/.local/share/1agent-ollama/dist/bin/ollama" serve \
  > "$HOME/.local/share/1agent-ollama/serve.log" 2>&1 &
echo $! > "$HOME/.local/share/1agent-ollama/serve.pid"

# 模型 + 16k 上下文
"$HOME/.local/share/1agent-ollama/dist/bin/ollama" pull qwen3:8b
printf 'FROM qwen3:8b\nPARAMETER num_ctx 16384\n' > /tmp/Modelfile.qwen3-16k
"$HOME/.local/share/1agent-ollama/dist/bin/ollama" create qwen3-8b-16k -f /tmp/Modelfile.qwen3-16k
```

### 4.3 并行 WorkItem 实测（2026-11-20）

一个 Goal 拆成 3 个独立 WorkItem（alpha/beta/gamma），`max_parallel=3`，
三个独立 workspace、三个 Ollama runtime profile，经真实 Workshop 0.11.1
派发。结果：

- 3 个 lease 决策在 4ms 内，3 个 session 在 1ms 内创建，执行区间重叠；
- 3 个 receipt 均 `completed`，每个 child 各有 1 次正确的 `write_file` 调用；
- 3 个 child journal `audit ok` + `replay ok`；
- Master journal audit 15 events / 0 issues；3 个 WorkItem 独立验收为
  `verified`（`verified_by=operator` ≠ 执行 Agent）；`goal_accepted=true`；
- 本地 8B 的 child answer 是 `needs_evidence`，但 artifact 真实存在；Master
  验收基于 artifact 检查，不依赖模型自述。

环境注意：默认 sessiond 已有 128 个活动会话，使用私有 sessiond；缺少
`skynet-workshop-lease` 别名，在私有 PATH 里指向 `skynet-term-lease`。
证据：`docs/evidence/parallel-workitems-ollama-2026-11-20/`。
未证明：同 workspace 并发写/合并、依赖 DAG、超 128 session、补偿路径。

### 4.6 规划器技能执行（2026-11-20）

- 新增 `skill_exec`：`master plan --allow-network` 时可运行
  `~/.1a/skill-exec.json` 声明的只读命令前缀；无 shell、最小环境、
  单次 90s / stdout 64k 字符上限；调用与观察进 planning journal。
- 首个配置：`lark-cli skills list/read`、`docs +fetch/+search`，
  用于在规划前读取飞书需求文档。`skill_search` 仍只发现、不执行；
  Worker 仍负责在工作区应用 skill。
- 边界：未配置或未传 `--allow-network` 时规划器看不到该工具；写命令和
  未声明前缀在工具层拒绝。文档：`docs/skill-exec.md`。
- 来源门禁：任务里的每个 `http(s)` URL 必须被成功 `skill_exec` 读取；
  `--source <URL|PATH>` 可声明额外来源。本地文件需 `read_file`/
  `read_document`，本地目录/第三方知识库需在其下成功读取或 `search_files`；
  未读返回 `UnreadSource`。Work Item 仍限制在 `context.workspace`。
- 类型化读取入口 `read_source`：模型只传 URL/路径，运行时选择 lark-cli

  证据 `docs/evidence/planner-read-source-2026-11-20/`。

  `docs/evidence/planner-plan-normalize-2026-11-20/`。

  `docs/evidence/planner-skill-exec-2026-11-20/`、
  `docs/evidence/planner-source-gate-2026-11-20/`。全量 lib

### 4.7 任务契约、拆解与验收（2026-11-20 研究结论）

研究结论：前沿正在从“模型自评/反思”转向
**spec/contract → task graph → independent executable verification →
progress ledger + replan**。1.2 Batch 2 按这个顺序重排：

- **TaskContract v1 已落地（2026-11-20）**：`PlanProposal.task_contract`
  （objective/deliverables/constraints/non_goals/sources/acceptance）；
  deliverable → work_item_ids 覆盖校验；CLI 模型生成器要求契约；
  DeepSeek 与本地 8B 实机均产出合法契约（8B: 3 deliverables → 4 Work
  Items）。证据 `docs/evidence/task-contract-v1-2026-11-20/`。
- **MA-003 已接线（2026-11-20）**：`master verify` 从 WorkItem 构造
  `AcceptanceContract`，运行时重算 artifact，`acceptance::close` 生成
  `CompletionReceipt`；只接受 `Accepted`；receipt 存入
  `VerificationResult.acceptance_receipt` 并进 journal。verifier ≠ executor
  仍强制。证据 `docs/evidence/acceptance-receipt-2026-11-20/`。
- **MA-006 已落地（2026-11-20）**：`TaskRuntimeState.progress` 记录最近动作/
  签名/stall 次数；相同 `Blocked`/`AwaitingInput` 原因重复 3 次 → `Replanning`
  + `Stalled`；不同原因、Running 心跳、提交或回执会重置。证据
  `docs/evidence/progress-ledger-2026-11-20/`。
- **MAST 故障注入已落地（2026-11-20）**：`tests/mast_fault_injection.rs`
  7 条负例覆盖假 SHA、缺 artifact、缺 criterion、自验收、重复/过期 receipt、
  未覆盖 WorkItem、重复 blocked/stall。证据
  `docs/evidence/mast-fault-injection-2026-11-20/`。

1. **TaskContract v1（任务理解/拆解）**
   - `objective`；`deliverables[{id, statement, acceptance, work_item_ids}]`；
     `constraints`、`non_goals`、`sources`、goal-level `acceptance`。
   - 校验：每个 deliverable 至少一个 WorkItem；每个 WorkItem 恰好归属一个
     deliverable；deliverable id 唯一；acceptance 非空；依赖图无环。
   - 模型负责内容，运行时校验覆盖；不按模型名分支。参考 Spec-Driven
     Development 的 requirements→design→tasks 与 EARS 可检查验收语句，
     但不做厚重模板（Thoughtworks 对过度规定的警告）。
2. **MA-003 独立可执行验收（已接线）**
   - 从 WorkItem 构造 `AcceptanceContract`；
   - verifier ≠ executor；优先 tests/SHA/schema 等可执行证据，而非文本自评；
   - 重算 artifact size/SHA；`acceptance::close` 生成 `CompletionReceipt`；
   - receipt 绑定 WorkItem/plan；`Accepted` 之外（Conditional/Rejected/Hacked）
     一律不接受。
   - 参考 Agent-as-a-Judge（会调工具的 verifier）与 self-preference 研究
     （独立模型/人类、可执行信号优先；评委团不能解决“一起错”）。
3. **MA-006 Task/Progress Ledger（已落地）**
   - 每个 WorkItem 记录 Task Ledger（已知事实/待验证/待推导/猜测）与
     Progress Ledger（完成？绕圈？有进展？下一步谁？）；
   - stall 计数超过阈值 → 重规划或拒绝。
   - 参考 Microsoft Magentic-One（arXiv 2411.04468）。
4. **MAST 评测与故障注入（已落地）**
   - 用 MAST 14 种失败模式（尤其 FC3：过早终止/无验证/错误验证）标注 trace；
   - 补 fake worker、假 SHA、自验收、stall、重复动作等负例；
   - 不把 happy-path smoke 当“work team 可信”的证据。
5. **Clarification gate（已落地）**
   - 拆解前检测不可自行发现的歧义（目标/约束/交付物），批量问一次；
   - 只问用户独有的信息，先探索可发现的事实；
   - 可逆/低风险先假设并继续，不可逆/高风险先问。
   - 模型返回 `needs_authorization`（最多 3 个 `unknowns` 问题），运行时
     只校验/展示，不按关键词判定；CLI 用 `--clarification` 带答案重跑，
     答案进入 `PlanningContext.clarifications`。生产规划路径同样生效。
   - 负例：4 问截断为 3、空/控制字符/超量答案拒绝、澄清不得被当成计划、
     清晰任务仍直接出计划；证据
     `docs/evidence/clarification-gate-2026-11-20/`（DeepSeek 实机一轮：
     3 问 → 带答案重跑得到 1 WorkItem / 2 artifact 的未批准计划）。
6. **MA-005 租约心跳/回收（已落地）**
   - live observation（poll/watch）是心跳；`heartbeat` 只延长未过期租约，
     旧 generation 或过期租约拒绝；
   - 过期租约先终止旧执行，再自动回收；前 2 次 → Retrying，之后 Blocked；
     终止失败保留租约给人工 reclaim；
   - generation 仍是 fencing token，旧收据在 reap 后和新租约下都被拒。
   - 负例：停心跳 → Retrying、旧 generation 收据 StaleReceipt、终止失败
     不自动重试、暂停时不回收；证据
     `docs/evidence/lease-heartbeat-reaper-2026-11-20/`。
7. **MA-007 子代理工具白名单（已落地，工具切片）**
   - `spawn_agent.allowed_tools` 是精确工具名白名单；父 runtime 有
     allowlist 时子代理继承，父有 + 子有取交集；空数组 deny all；
   - `ToolRegistry::restrict_to` 拒绝未知工具名，过滤 specs/capabilities，
     execute 对隐藏工具返回 `tool_not_allowed`；子进程用
     `--allowed-tools`/`--deny-all-tools` 落地；
   - `required_capabilities` 仍是 WorkItem 分配元数据，没有运行时
     能力→工具映射，本切片不声称强制。
   - 负例：父/子交集、继承、空数组、非法名、运行时只广告 allowlist；
     证据 `docs/evidence/subagent-tool-allowlist-2026-11-20/`。

**不做**：重型 step-level PRM/奖励模型、评委团、过度规定的小 DSL、

## 6. 风险与回滚

- **MA-001 可能打破旧的 fake-program 测试**：测试 fake 必须写最小合法 journal，
  或显式 test-only opt-out；生产路径默认 fail closed。
- **MA-002 可能放大 tool result**：结构化答案上限 8 KiB；全文留 child journal。
- **MA-004 字段可选**：`#[serde(default)]`，旧 registry/journal 继续可读。
- **Ollama 8B 在 8GB VRAM 上可能慢**：16k 上下文允许 CPU offload；质量不作为门禁。
- **回滚**：Batch 1 的契约字段均为 optional；fail-closed 没有生产关闭开关。
  旧 fake harness 使用 `#[cfg(test)] allow_missing_journal` 显式 opt-out。
