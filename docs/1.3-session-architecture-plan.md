# 1.3 — durable session architecture (2026-11-21)

Status: **Phase 0 and the Phase 1 session MVP landed (2026-11-21)**. Not a
release; version remains `1.0.0-rc.13`.

## Why

Two same-task runs and one failed follow-up exposed the same gap from different
angles:

- 2026-11-20: 59 model calls / 68 tool calls / 365s.
- 2026-11-21: 66 model calls / 81 tool calls / 439s; same final status
  (`conditional`).
- Every model call carried **5,880 system + 6,034 tool-schema tokens = 11,914
  fixed tokens**, and advertised **38 tools**.
- The follow-up “不要带有任何静态文件，都写入一个html当中” died before the
  first model call: `infer_mode` saw “写入” → `CognitiveMode::Execute` →
  `risk_for_mode = High`; the only provider (`deepseek`) has `max_risk =
  Medium`, so the route plan had no candidate.
- The build run that actually wrote files was labelled `DirectAnswer` / `Low`
  risk, because its wording did not contain an execute keyword. Risk followed
  wording, not permissions or actions.

P0 (work ledger + Answer/Ask/Act) fixed a different problem: provenance
questions. It does not make Act tasks faster and it does not provide
conversation continuity.

## Reference designs

| System | Session model | What to take |
|---|---|---|
| Pi 1.5.2 | JSONL tree; active branch → context projection; compaction entries with `firstKeptEntryId`; steering vs follow-up queue; plain-text final | session tree, projection, steering, compaction |
| opencode 2.3.2 | SQLite session DB; message parts (`reasoning`/`text`/`tool`); instruction deltas; hidden compaction/summary/title agents; synthetic resume message; idle outcomes; persisted permissions | reasoning as a part, instruction deltas, helper agents, resume |
| grok shell | 103-line streaming chat, 0 tools, ~1s | latency baseline only; not a task baseline |

## Target architecture

```
run journal (per run, audit)  ── append ──▶  session tree (per conversation)
                                                   │
                                      context projection (active branch)
                                                   │
                                      model call → tool loop → next turn
```

- The run journal stays the audit record. The session tree is the durable
  conversation state and the source of model context.
- A follow-up is a new message on the same session branch, not a new run with
  profile/preflight/route/gates.
- Reasoning is a first-class, streamed part.
- Instructions are deltas (`core/instructions`, `core/date`, `core/skills`,
  `core/mcp`), not a 5.8k block re-sent every call.
- Compaction, summary and title run as hidden helper agents. The main loop only
  reasons and calls tools.
- Delivery tasks keep acceptance, evidence and the work ledger. Chat/answer
  tasks get a thin path.

## Phases

### Phase 0 — route/risk consistency (this commit)

- Add `risk_for_run(InteractionMode, allow_write)`:
  - Answer / Ask → Low;
  - Act + `allow_write` → High;
  - Act without write → Medium.
- Use it for `RouteRequest.risk` instead of `risk_for_mode(CognitiveMode)`.
- `NoRoute` names the requested risk and every rejected candidate, e.g.
  `requested risk high; rejected deepseek/deepseek-flash: RiskExceeded`.
- Next-action text points at `providers[].max_risk` in `~/.1a/config.json`.
- Raise the local provider `max_risk` to `high` (with a config backup) so the
  approved full-local workflow can route Execute tasks.
- Tests: risk mapping; fmt/clippy/lib; a live Execute-mode run starts.

### Phase 1 — session MVP

- `src/session.rs`: JSONL session store with session header, message parts
  (user / assistant / tool / reasoning), instruction deltas, compaction,
  synthetic notices, idle outcome.
- `AgentRuntime` loads context from the active session branch at run start and
  appends the run's messages at the end. The per-run journal is still written.
- CLI/TUI: continue the active session (`--continue-session` / session id);
  follow-ups append; only a new Act task runs task profile + capability
  preflight + route planning.
- Synthetic resume message after a process restart: continue without repeating
  completed work.
- Tests: build→question, build→modify, build→new version in one session; assert
  one route plan, no capability preflight on follow-ups, old artifact unchanged
  or edited as expected.

**MVP landed:** `src/session.rs` stores a JSONL transcript per workspace and
session id (`~/.1a/sessions/<workspace-hash>/<id>.jsonl`,
`ONEAGENT_SESSION_DIR` overrides) with user/assistant messages and synthetic
notices. Context projection keeps the last 20 messages within 24k characters.
`AgentRuntime::with_session_path` loads that context before the current user
message, appends the user turn before the run and the assistant turn after it;
an unanswered last user turn gets a synthetic resume notice on the next run.
The per-run journal is unchanged. CLI: `1agent run --session <id>` and
`--continue-session`. TUI: the existing `TuiSession` id + workspace now select
the conversation session automatically.

**Continuation:** a session with prior turns skips capability preflight; only a
new session compiles a capability contract. Act continuations still route,
edit the active artifact, and keep acceptance; Answer continuations keep the
tool mask.

Evidence: session round-trip and runtime two-run tests; live CLI first run
“记住：我叫测试” followed by `--continue-session` “我叫什么？” answered “测试”,
with the prior user and assistant turns present in the second model request.

repeat are in `docs/evidence/session-followup-2026-11-21/`: build had
preflight=1, modify had preflight=0 and edited `index.html` in place
(`c60e48aa…` → `a2dccec3…`), question made one model call, used no tools, and
left the file untouched. Installed binary build 29s / modify 22s.

Deferred to the next slice: steering queue, tool/reasoning parts in the

### Phase 2 — context economics

- Instruction deltas + instruction state; system prompt built from base +
  deltas.
- Reasoning part streamed in the TUI and stored in the session.
- Default tool surface 6–8; the rest via `tool_search`. Target: system + tool
  schema under 4k tokens.
- Hidden compaction/summary/title agents; the main loop never generates a
  summary.

Exit: fixed per-call overhead measured and reduced; no 38-tool advertisement.

### Phase 3 — delivery quality

- Ledger freshness for `terminal_exec`-generated artifacts: files named by a
  receipt/answer whose mtime is after run start are recorded as fresh, not
  reused.
- Acceptance contract template includes mobile tap-target and brief-completeness
  checks, or accepts browser-audit evidence for them.
- Fast answer path: one streaming completion, no tools, no structured answer;
  target under 3s.
- Answer starts with the artifact path; auxiliary files are labelled as scratch.
- Optional TUI session-end rating: one line, `1` bad / `2` fine / `3` good /
  `0` dismiss, local only in `~/.1a/session-ratings.jsonl`, skipped when stdin
  is not a TTY. **Landed 2026-11-21**; verified by driving the installed TUI
  through tmux (`/quit` → `3` → `rating: good`).

### Phase 4 — measurement

- Arms: full 1agent, minimal Act, Pi; same task, same model, same endpoint
  (`127.0.0.1:8787`); N=3.
- Metrics: model calls, wall time, TTFT, fixed tokens, tool calls, completion,
  user corrections.
- Feature flags and rollback; no big-bang rewrite.

## Non-goals

- Do not remove acceptance/evidence/ledger for delivery tasks.
- Do not copy opencode's no-audit model.
- Do not add more keyword gates.
- Do not move to SQLite/event sourcing unless JSONL proves insufficient.

## Risks

- `max_risk = high` lets Execute tasks route to the remote DeepSeek endpoint.
  This is a user-approved security decision.
- A session layer duplicates the journal; keep the journal as the audit source
  and the session as the context projection.
- Compaction summaries can drop detail; retain raw journal entries.
