## 2. ADR 流程

重大决策必须先 ADR，后实现。重大包括：

- 新增/删除领域概念；
- 权限模型、沙箱、密钥；
- 存储/队列/Web 框架/部署形态；
- 记忆/技能的生命周期与自动写入；
- 对外承诺、发布门禁；
- 与现有文档冲突的任何设计。

ADR 模板：

```markdown
# ADR-XXX: 标题

Status: proposed | accepted | superseded | rejected
Date:
Deciders:
Related: 章节/工作包

## Context
为什么现在要决定？约束是什么？

## Decision
决定是什么？必须/禁止什么？

## Alternatives
考虑过什么？为什么没选？

## Consequences
正面/负面/风险/迁移。

## Verification
怎么证明决定被执行？测试/命令/指标。
```

ADR 存放：`docs/adr/`（沿用现有目录），索引在本文 §4。

## 6. 一致性协议

### 6.1 写代码前

1. 找到对应章节与工作包。
2. 检查术语是否在 `001-domain.md` 登记。
3. 检查是否违反六条不变量（`000`）。
4. 检查是否与 `docs/product-boundary.md`/`docs/self-evolution.md` 冲突；冲突先开 ADR。
5. 写清楚验收标准（可测试）。

### 6.2 提交前

- [ ] 术语一致（没有新造词/同义词混用）。
- [ ] 状态机转换合法，非法转换有测试。
- [ ] 权限链完整（Worker ⊆ Ticket ⊆ Bot ⊆ Policy）。
- [ ] 记忆不授权；技能不越权。
- [ ] journal 事件齐全；可重放。
- [ ] 敏感信息不落盘。
- [ ] 文档链接有效；所有者文档已更新。
- [ ] `./scripts/verify.sh` 通过。
- [ ] 外部声明有 `docs/claims.md` 证据。

### 6.3 评审时

评审必须显式回答：

1. 这个改动属于哪个工作包/章节？
2. 是否引入新术语？登记了吗？
3. 是否改变了状态机/权限/记忆/技能契约？
4. 失败/停止/回滚路径是什么？
5. 测试能证明什么、不能证明什么？

## 7. 矛盾检查清单

出现以下情况，视为文档/实现矛盾，必须修复：

- 同一概念在两个文档定义不同。
- 代码里有未登记的术语/状态。
- UI 显示的状态与 journal 不一致。
- 权限在文档里是 A，代码里是 B。
- 记忆/技能能改变权限。
- 声称"完成"但没有 artifact/journal。
- Roadmap 说未开始，代码已默认开启。
- 测试通过但只覆盖 happy path。
- 对外声明没有 claims 证据。

## 8. 弃用与迁移

1. 标记 `deprecated`，写替代方案与迁移步骤。
2. 保留至少一个版本周期；双写/双读。
3. 更新 API/schema/文档/测试。
4. 删除前确认无引用；保留 ADR 记录。
5. 对外发布说明。

## 10. 变更节奏

- 每周：更新工作包状态、风险、开放问题。
- 每阶段：门禁评审、ADR 归档、claims 复核。
- 每次发布：CHANGELOG、回滚方案、已知限制。
- 每季度：架构复盘，删除过时文档/概念。

## 11. 最后一条

**手册不是装饰。**  
如果代码与手册冲突，先停下，开 ADR，改文档，再改代码。  
不允许"先实现，文档以后补"——那正是前后矛盾的来源。
