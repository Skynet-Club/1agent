# 005 技能与自我进化

Status: design normative; L0–L2 已有基础，L3 仅限受控实验，L4 不做  
Depends on: `001-domain.md`、`004-memory.md`  
Owns: 技能格式、进化闭环、评测门禁、回滚  
Does not own: 记忆检索（`004`）、运行时执行（`006`）

## 1. 先定义"进化"

进化不是"模型改自己"，而是：

> 从成功与失败中提炼可复用的**策略/流程**，在离线评测中证明它更好，再以版本化、可回滚的方式投入使用。

四个层级：

| 层级 | 改什么 | 风险 | 1A 策略 |
|---|---|---|---|
| L0 | 不学习 | 无 | 基线 |
| L1 | 上下文/提示策略 | 低 | 允许，需评测 |
| L2 | 记忆/经验/技能（不改进权重） | 中 | **当前主路径**，需审批 |
| L3 | 代码/架构自改 | 高 | 仅沙箱 + archive + 人工监督的实验 |
| L4 | 权重更新/微调 | 极高 | 不做产品承诺，仅研究 |

与 `docs/self-evolution.md` 一致：当前 L2 已实现；本文件扩展 L1/L3 的边界，不重新定义 L2 生命周期。

## 2. 两个系统：Memory vs Skill

| | Memory | Skill |
|---|---|---|
| 内容 | 事实、偏好、决定 | 流程、步骤、判断规则、坑 |
| 大小 | 小，常驻/按需 | 大，渐进披露 |
| 加载 | 每次相关时检索 | 只在任务匹配时加载 |
| 例子 | "用户用 pnpm" | "如何发布 1A 版本" |
| 失败 | 记错事实 | 套错流程 |

规则：

- 事实不要写成技能；流程不要塞进记忆。
- 技能可以引用记忆，但不得把一次性事件叙事写进技能。
- 技能不得包含密钥、个人隐私、完整对话。

## 3. 技能格式

采用与 Claude Code / Hermes / agentskills.io 兼容的 `SKILL.md`：

```markdown
---
name: release-1a
description: 发布 1A 版本的完整流程（≤60 字符）
version: 1.2.0
platforms: [linux, macos]
metadata:
  scope: repo:1-agent
  requires_tools: [shell, git, cargo]
  risk: medium
---

# Release 1A

## When to Use
当需要发布新版本时。

## Procedure
1. 确认版本号与 CHANGELOG。
2. 跑 `./scripts/verify.sh`。
3. 构建 release，校验 SHA-256。
4. 打 tag，推送，生成 release notes。

## Pitfalls
- 不要在未通过门禁时打 tag。
- 不要在 dirty worktree 上发布。

## Verification
- `verify.sh` exit 0。
- release manifest 与源 commit 绑定。
```

规则：

- `name` 唯一；`description` 用于索引，不加载正文。
- 正文只在被调用/匹配时加载（渐进披露）。
- 技能可以有 `references/`、`scripts/`、`templates/`，按需读取。
- 技能版本不可变；修改生成新版本。
- 技能必须声明适用平台、工具、风险、scope。

## 4. 渐进披露

```text
Level 0  skills_list()        → name + description（~几百 token）
Level 1  skill_view(name)     → SKILL.md 正文
Level 2  skill_view(name, p)  → references/scripts 中的具体文件
```

规则：

- 系统提示只放索引，不放正文。
- 正文超过约 24k 字符要拆分到 `references/`。
- 一个技能只解决一类任务；不要做"万能技能"。
- 技能内容要"少而准"：步骤、判断规则、坑、验证；不要叙事。

## 5. 候选生成

触发时机：

- 任务成功且流程非平凡；
- 任务失败并找到修复路径；
- 用户纠正了 Bot 的做法；
- 同类任务重复出现（≥2 次）；
- 定期复盘（每周/每项目）。

候选内容：

- 一条可复用的流程/策略；
- 适用范围（repo/项目/模式）；
- 证据链接（run/ticket/event）；
- 预期收益（更快/更准/更省）；
- 风险与回滚方式。

规则：

- 每次最多 1–2 条候选；宁缺毋滥。
- 候选先进入 `draft`，不改变行为。
- 去重：与现有技能/记忆相似则合并或拒绝。
- 无证据的候选直接拒绝。

## 6. 评测门禁

候选必须通过：

| 门禁 | 要求 |
|---|---|
| 证据 | 来源 run/ticket 存在且未篡改 |
| Held-out | 训练/评估分组不重叠 |
| 效果 | 成功率提升，或成本/时延显著下降 |
| 负迁移 | 不相关任务不退化 |
| 安全 | 不引入越权、注入、密钥泄漏 |
| 成本 | token/时间在预算内 |
| 可复现 | 评测可重跑，记录版本/摘要 |

流程：

```text
draft
  → 离线评测（baseline vs candidate）
  → shadow（只记录，不影响用户）
  → 人工/自动审批
  → active
  → 监控效用
  → degrade / rollback
```

规则：

- 默认人工审批；只有低风险、可逆、评测充分时才允许自动。
- Shadow 期至少覆盖 N 个真实任务（N 由风险决定）。
- 激活后持续监控；效用下降自动降级/回滚。
- 技能/记忆的激活都走同一套状态机（见 `001-domain.md`）。

## 7. 技能治理

- **来源**：内置、团队、社区、Agent 自建。
- **扫描**：注入、凭据、隐藏字符、危险命令、许可证。
- **签名**：摘要 + 可选签名；安装时校验。
- **隔离**：首次运行需审批；只能在 Ticket 权限内执行。
- **锁定**：Owner 可锁定关键技能，禁止自动修改。
- **弃用**：新版本发布不删除旧版本；标记 deprecated，保留回滚。
- **审计**：谁创建/修改/批准/使用，全部留痕。

## 8. 代码/架构自改（L3）

只允许在沙箱 + archive + 人工监督下进行：

1. 候选变体在独立分支/沙箱中生成；
2. 跑固定基准（SWE-bench 类 + 1A 自有套件）；
3. 结果进 archive，不直接替换生产；
4. 人工审查后合并；
5. 保留回滚。

禁止：

- 生产环境自改代码；
- 无基准的自改；
- 自改权限/审计/策略代码；
- 自改后自动发布。

DGM/SEAL 是研究参考，不是产品路线。

## 9. 失败模式

| 失败 | 表现 | 防线 |
|---|---|---|
| 奖励黑客 | 只优化指标，不解决任务 | 多指标 + 人工抽检 |
| 过拟合 | 只在评测集上好 | held-out + 新任务 |
| 负迁移 | 经验套错场景 | scope + 负迁移测试 |
| 技能蔓延 | 数百个重复技能 | 去重 + 合并 + 退役 |
| 记忆污染 | 恶意内容固化 | taint + 审批 + 回滚 |
| 自动漂移 | 长期慢慢变差 | 效用监控 + 定期回归 |
| 成本失控 | 记忆/技能检索过重 | 预算 + 缓存 |

## 10. 指标

| 指标 | 定义 |
|---|---|
| Skill reuse rate | 被复用的技能 / 总技能 |
| Success delta | 使用技能 vs baseline 的成功率差 |
| Negative transfer | 套用后失败的比例 |
| Time-to-skill | 从首次任务到技能可用 |
| Skill sprawl | 重复/低效技能数量 |
| Drift | 激活后效用下降幅度 |
| Rollback rate | 回滚比例 |

## 11. 实施顺序

1. 技能格式 + 索引 + 渐进披露。
2. 候选生成（反思）+ 证据链接。
3. 离线评测 + shadow。
4. 审批/激活/监控/回滚。
5. 技能市场 + 安全扫描（后续）。
6. L3 实验（更后续）。

## 12. 开放问题

- 自动生成的技能如何避免"看起来合理但不可用"？
- 技能之间的冲突/优先级如何裁决？
- 跨项目/跨用户的技能共享边界？
- 技能评测的任务从哪来、如何防泄漏？
- 长期运行后技能库如何保持精简？
