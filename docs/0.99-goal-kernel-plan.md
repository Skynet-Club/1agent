## 0. 一句话

0.98.2 回答“发生过什么、证据在哪里”；0.99 回答“要达成什么、下一步做什么、
谁负责、做完后凭什么算完成”。目标是把现有的 goal/commitment、action card/log、
sub-agent registry 从三个相邻模块，接成一条可恢复、可授权、可验收的执行链。

## 1. 定位与边界

### 1.1 必须交付

1. **GoalKernel**：Goal、Commitment、Run、Task、Answer 之间的稳定绑定；
   目标状态、承诺截止、完成/放弃的可审计转换。
2. **ActionRuntime**：每个副作用动作有统一记录：run/session、ActionType、
   风险/可逆性、policy decision、approval、执行结果、artifact hash。
3. **DelegationKernel**：队员记录真正带上父会话、父 run、spawn 调用和子 run；
   支持深度/扇出、失败/超时、结果回收和人工接管。
4. **Closure evidence**：目标关闭必须引用答案、验证记录和未满足承诺；不能只靠
   “模型说完成了”。
5. **0.98.2 缺口闭合**：SquadMember 的 parent session/run、R6 policy/approval
   metadata、动作日志与 journal 的关联。
6. **可验证门禁**：目标/动作/委派三条 CQ 链、故障注入、replay、权限负例。

### 1.2 明确不做

- 不做完整 OWL reasoner、图数据库、A2A/OTel 全量接入。
- 不做无限制自主性；高风险/不可逆动作仍需显式授权。
- 不做“目标一创建就自动无限分解”的规划器；分解仍是模型/人协作。
- 不把 commitment 变成催办 UI；只在用户需要时呈现。
- 不改变 journal 为事实源；goal/action/delegation 记录必须能 replay。

## 2. 领域模型

### 2.1 四个不同概念

| 概念 | 含义 | 不相等 |
|---|---|---|
| Goal | 想要达成的世界状态 | 不是一次运行 |
| Commitment | 对某人/某时的承诺 | 不是任务清单 |
| Task | 一次可执行的工作单元 | 不是答案 |
| Answer | 对当前问题的结论 | 不是目标完成 |
| Outcome | 实际改变后的状态/验证结果 | 不是模型声明 |

现有 `src/goal.rs` 已有 Goal/Commitment/GoalEvent/GoalStore；0.99 增加与
run/session/action 的引用，不重写其 hash-chain 语义。

### 2.2 稳定 ID 与绑定

| 实体 | ID/绑定 |
|---|---|
| Goal | `urn:1agent:goal:<goal-id>` |
| Commitment | `urn:1agent:commitment:<commitment-id>` |
| Run | 现有 run UUID |
| Session | 现有 session id |
| Task | `urn:1agent:task:<run>:main` |
| Action | `urn:1agent:action:<run>:<action-id>` |
| Delegation | `urn:1agent:delegation:<parent-run>:<spawn-call>` |

Goal 与 session 的绑定是显式的 `session.goal_id`；一个 session 可以有多条 run，
但只能有一个 active goal revision。Goal 关闭不等于 session 删除。

### 2.3 状态机

Goal: `active -> paused|achieved|abandoned`，`paused -> active|abandoned`。
Commitment: `pending -> kept|missed|cancelled`；`kept/missed/cancelled` 终态。
Action: `proposed -> allowed|denied|needs_approval -> approved|rejected ->
executed|failed|cancelled`。不允许从 `needs_approval` 直接到 `executed`。

## 3. GoalKernel

### 3.1 API 草案

```rust
pub struct GoalBinding {
    pub goal_id: String,
    pub session_id: Option<String>,
    pub run_ids: Vec<String>,
    pub commitment_ids: Vec<String>,
}

pub fn link_session_goal(session: &mut TuiSession, goal_id: &str) -> Result<(), GoalError>;
pub fn link_run_to_goal(store: &mut GoalStore, goal_id: &str, run_id: &str) -> Result<(), GoalError>;
pub fn close_goal_with_evidence(
    store: &mut GoalStore,
    goal_id: &str,
    outcome: GoalOutcome,
) -> Result<(), GoalError>;
```

`GoalOutcome` 至少包含：`answer_run_id`、`verification`（passed/failed/unknown）、
`open_commitment_ids`、`reason`。关闭规则：

- `achieved` 需要至少一条 completed run + 验证通过；否则只能 `paused` 或
  `abandoned`，并记录未满足项。
- `abandoned` 必须记录原因；未关闭 commitment 标 `cancelled` 或保留 pending 的
  理由。
- 关闭后不删除历史；新目标必须新 goal_id。

## 4. ActionRuntime

### 4.1 单一动作记录

现有 `src/action_log.rs`、action card、Authority/ExecutionGate 分离。0.99 增加
一个只读投影 + 一个写入适配层，不复制策略引擎：

```rust
pub struct ActionRecord {
    pub action_id: String,
    pub run_id: String,
    pub session_id: Option<String>,
    pub action_type: String,
    pub risk: RiskLevel,
    pub reversible: bool,
    pub policy_outcome: PolicyOutcome,
    pub policy_reason: Option<String>,
    pub authority_profile_id: Option<String>,
    pub approval_card_id: Option<String>,
    pub status: ActionStatus,
    pub artifact_sha256: Option<String>,
}
```

`ActionRecord` 写入 action log，同时把最小字段写进 journal `ToolObserved.metadata`
或专用 `ActionRecorded` 事件；两者必须能对账。

### 4.2 规则

- Authority/Policy 仍是唯一 allow/deny 源；ActionRuntime 不重新判定。
- 不可逆/高风险动作在 `needs_approval` 时不得调用工具。
- 审批 card 绑定 action_id + expected artifact SHA；审批后 SHA 变化必须重新审批。
- 动作失败/超时/取消也记录；不能只记录成功。
- 导出只记录类型/风险/策略结果/引用，不记录工具参数正文。

| ID | 任务 | 验证 |
|---|---|---|
| AR-001 | ActionRecord schema + migration | 旧 action log 可读 |
| AR-002 | runtime gate 写入 policy/approval metadata | allow/deny/approval 三例 |
| AR-003 | action log ↔ journal 对账 | 缺一即错误 |
| AR-004 | irreversible/approval SHA 绑定 | 审批后漂移拒绝 |
| AR-005 | ontology ActionInvocation/PolicyDecision/Approval | CQ12/CQ16 |
| AR-006 | `1agent action show|verify` CLI | 负例 exit nonzero |

## 5. DelegationKernel

### 5.1 目标

队员记录从“有 id/状态”变成“有父会话、父 run、spawn 调用、子 run、结果引用”，
并支持失败/超时/取消的可审计处理。

### 5.2 接线

- AgentRuntime 增加 `RunContext { run_id, session_id, goal_id }`；在工具执行时
  通过 task-local 传入 SpawnAgentTool。
- `SubagentRecord` 写入 `parent_session_id`、`parent_run_id`、`spawn_call_id`；
  子进程返回后写 `child_run_id`。
- 子 run 的 journal 与父 run 的 spawn observation 双向引用。
- 扇出/深度限制保持不变；超过限制必须失败并记录原因。
- 子代理失败/超时：父 run 得到结构化 observation，不得伪装成 completed。

### 5.3 任务

| ID | 任务 | 验证 |
|---|---|---|
| DK-001 | RunContext task-local | 并发 run 不串线 |
| DK-002 | parent session/run 写入 | registry 100% 字段完整 |
| DK-003 | child run 反向引用 | 父子链可 replay |
| DK-004 | 失败/超时/取消矩阵 | 父结果与 registry 一致 |
| DK-005 | ontology SquadMember | CQ4/CQ13 |
| DK-006 | TUI 分队血缘摘要 | 只读展示，不改布局 |

## 6. 验收与门禁

### G0 合同冻结

- GoalBinding/ActionRecord/DelegationContext schema 冻结。
- 文件所有权、迁移规则、CQ 清单、回滚分支确定。

### G1 Goal 链

- Goal→session→run→answer 可查询；无证据关闭失败；旧日志兼容。
- CQ：目标是否完成、哪些承诺未完成、哪条 run 支撑。

### G2 Action 链

- 每个副作用动作有 policy/approval/outcome；allow/deny/approval 三例。
- 不可逆动作未审批不得执行；审批后 SHA 漂移拒绝。

### G3 Delegation 链

- 100% 新 spawn 记录有 parent session/run/spawn call/child run。
- 失败/超时/取消不产生虚假 completed；扇出/深度负例通过。

### G4 Super-Agent 验收

- 10 条真实多步任务：目标关闭有证据、动作可追溯、队员结果可回收。
- 无 P0 安全/权限/隐私问题；replay 100%；无新增 unsupported completed。
- 质量/延迟相对 0.98.2 基线不下降，除非有 A/B 证据并获 owner 批准。

## 8. 风险

| 风险 | 缓解 |
|---|---|
| Goal/Commitment 变成催办负担 | 默认静默；只在状态变化/用户查询时呈现 |
| ActionRuntime 复制策略引擎 | 只做记录/投影；Authority 仍是唯一判定 |
| 父 run context 串线 | task-local + 并发测试；禁止全局可变单例 |
| 旧记录不兼容 | `serde(default)` + migration tests；不重写历史 |
| 范围膨胀到 A2A/OTel | 0.99 不做；1.0 再评估 |
| 目标关闭被模型自证 | 需要独立 verification/evidence；unknown 不升级 |

## 9. 与 1.0 的关系

0.99 完成后，1.0 才具备“可信 Super-Agent”的内核：

- 目标可关闭、承诺可追踪、动作可授权、队员可追溯。
- SDK/API、团队/跨平台、外部审计才有稳定对象可暴露。
- 若 0.99 的 CQ/门禁不成立，不进入 1.0 的对外承诺。
